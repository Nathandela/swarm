# ADR-015: The push gateway splits from the relay — Swarm operates the FCM sender, `swarm-remote` submits the wake, Android is the first client

## Context

### What the repository actually does today

Push is relay-resident, end to end, and every seam says so in its own comments:

1. **The relay holds the sender credential.** `relay.Config.PushCredentials` is "the path to a Google service-account JSON document. Set, the shipped binary constructs the FCM sender (`internal/remote/push`) and injects it via `WithPushSink`" (`internal/remote/relay/config.go:57-64`). `cmd/swarm-relay/main.go:78-94` reads that file, calls `push.LoadServiceAccount` and `push.NewFCM`, and installs the result as a `relay.Option`. Its own doc comment already records the scope limit: "this wiring has never run against Google. There is no account in this project, PB-E2E-5 (real provider, real handset) remains DEFERRED" (`main.go:75-77`).
2. **The FCM client is complete and correct, and it is the asset this ADR relocates rather than rewrites.** `internal/remote/push` carries the v1 sender (`fcm.go`), the RFC 7523 JWT-bearer OAuth exchange with a single narrow `messagingScope` (`oauth.go:19-22`), service-account parsing (`serviceaccount.go`), retry-versus-refuse and `UNREGISTERED` classification (`fcm.go:102-131`, `:195`), and a request body whose three load-bearing properties are already argued in place: data-only so no provider-composed text reaches a lock screen, `android.priority` high because B16 makes high-priority FCM the sole background wake path, device token never a topic, and exactly one data key (`fcm.go:150-158`).
3. **The relay owns the token mapping and has two push producers — both of which are now correctly shaped and rate-charged, and this ADR must not claim credit for that.** `handleTokenRegister` (`internal/remote/relay/server.go:1092`) persists a provider-issued token keyed by routing id and `handleTokenDelete` removes it (`:1125`). `handlePushTrigger` (`:1204`) delivers the machine's wake; it **refuses any envelope that is not exactly `PushEnvelopeSize` = 78 bytes, before the quota** (`:1230-1232`). `SweepPresence` (`:1732`) delivers the liveness push, and it is **charged against the same window as the trigger**: "CHARGED AGAINST THE TARGET'S PUSH WINDOW, exactly as push_trigger is (round-4 threat review H2). This path used to call deliverPush directly while pushRate guarded only the handler" (`:1754-1774`). Its ciphertext is `silentWakeCover()`, `PushEnvelopeSize` random bytes chosen so the sweep is the same size *and* the same content class as a gateway wake (`internal/remote/relay/push.go:41-67`). The client op is still named for Apple: "TokenRegister registers (or refreshes) this device's APNs push token" (`internal/remote/relay/client.go:903`), called from `mobile/relay.go:650` and `mobile/app.go:1387-1403`.
4. **The machine-side wake producer is already minimal, already content-free, and already the right shape.** `internal/remotegw.PushNotifier` takes a `WakeKey` and **no** content key — "what is enforceable, and what the criterion protects, is that the PUSH PATH holds the wake key only" (`push.go:43-67`), enforced reflectively by `TestPBPUSH0_PushConfigCarriesNoContentKey` (`internal/remotegw/push_trigger_test.go:478`) — coalesces at most one wake per session per 30 s (`push.go:14-18`, pinned by `TestPBPUSH0_CoalescesRepeatTransitionsWithinTheWindow`, named at `push.go:340` and defined at `push_trigger_test.go:399`), defers rather than drops a suppressed interaction wake (`push.go:329-359`), wakes only **after** a successful mailbox append and never fails a record on a push error (`push.go:180-198`), and seals an empty plaintext with both endpoint key ids left at zero into a size pinned as a constant: `PushWakeEnvelopeSize = 78` (`push.go:20-29`), fenced by `TestPBPUSH3_WakeEnvelopeIsExactlyTheFixedContentFreeSize` (`push_trigger_test.go:503`).

The seam between (4) and (1) is one relay op. Everything above is what survives; the credential, the token map and the transport are what move.

### The one push residual the relay cannot close from where it sits

Item 3 above closed two recorded findings — B70-H2's unrated sweep (`ADR-007:3651-3655`) and B70-Q1/B77's shape separation (`ADR-007:3665-3672`, `:1841-1848`). It did not close the third, and `silentWakeCover`'s own comment says so in the place an implementer will read it:

> "A genuine wake's envelope header is CLEARTEXT — version, type, epoch id, seq and issued_at (ADR-007 B70-Q1/B77, a recorded trade the replay window rests on) — so a provider that PARSES rather than measures can still tell a wake from this. Closing that needs either a key the relay must not hold or dropping the sweep's push entirely, and **both are decisions above this seam**." (`internal/remote/relay/push.go:56-60`)

**This ADR is the decision above that seam**, and it takes the second branch: the relay loses its push transport, so it has no producer to separate (P10). That, and not B70-H2, is what this document discharges.

### What ADR-007 decided, and the sentence that scheduled this ADR

D12 named this exact seam and deferred it on an explicit premise: "The blind-push-gateway seam (relay cannot hold the APNs signing key if the app is ever distributed) is a conscious deferral, **moot for the personal-only build**" (`ADR-007:94`). **This ADR is that deferral coming due.** The premise expires at Play distribution: the application's Firebase sender credential is one credential for one Play-signed package, and there is no version of RC-D2's "every developer or organization operates its own relay" (playbook `:72`) in which that credential is copied onto every operator's VPS. `PushCredentials` is not a configuration item that a self-host operator can fill in; it is a configuration item that only Swarm can fill in, sitting in the one component Swarm does not operate.

Three further ADR-007 statements are factually wrong the moment Android ships and are amended here rather than left to rot: D9's "forwards push wakes to APNs" and "an APNs push-token registration/refresh/deletion op" (`:78`), D11's "Apple sees push routing and timing" (`:88`), and the 2026-07-23 amendment's "iOS AND Android, both first-class" (`:286-296`). The playbook's §15 lists iOS as a non-goal for the first complete product (`:1018`).

### Why the load-bearing claim cannot be softened

B16 decided to drop the socket in every background state and accepted the consequence in writing: "Push is now **load-bearing, not a convenience**. A dropped push is a missed hand-off with no fallback" (`ADR-007:1144-1145`). That is why "ship without push" is not on the table below, and why the gateway's availability is a product property rather than an operational detail. B143 (`ADR-007:8581`) already disclosed, on the Settings screen, that Doze and battery saver delay these wakes; that disclosure is unchanged and its wording is not a casualty of this move.

### The Firebase facts, so nothing here is a forecast

Firebase project `swarm-8404f` exists; the Android app `dev.swarm.phone` was registered on 2026-08-14; the FCM v1 API is enabled; the sender/project number is `733314021126`. The client config sits at `android/app/google-services.json`, present locally and deliberately untracked — `.gitignore:60-62` records why: "Present locally so Wave R3 can apply the google-services plugin; stays out of the repo until R3 decides how config ships." No production token has been collected, no Google Services plugin is applied, and PB-E2E-5 remains DEFERRED. Every delivery claim in this ADR is therefore a design commitment, not evidence.

## Decision

**P1. The FCM sender leaves the relay. `swarm-relay` ships with no push credential, no token map, and no push transport.** `relay.Config.PushCredentials` (`config.go:57-64`) and `cmd/swarm-relay/main.go`'s `pushOptions` (`:64-94`) are removed, not merely left empty. The protocol case labels `token_register` (`server.go:694-695`), `token_delete` (`:696-697`) and `push_trigger` (`:700`) leave the public relay protocol on the schedule P12 sets, together with their handlers (`:1092`, `:1125`, `:1204`). The relay keeps its mailbox, presence, rendezvous and quota surfaces exactly as they are. Playbook §6.5's closing line is the test of whether this ruling landed: "The relay remains usable without push credentials because push no longer lives there" (`:510`).

**P2. `internal/remote/push` relocates verbatim; only its import direction inverts.** The OAuth exchange, the narrow scope, the retry/`UNREGISTERED` classification and the data-only high-priority body are the reviewed work of the push slice and are re-hosted, not re-derived. One structural consequence must be planned rather than discovered: the package is currently defined *against* the relay — `var _ relay.PushSink = (*FCM)(nil)` (`fcm.go:17-18`) and `Push(ctx, token string, p relay.PushPayload)` (`fcm.go:102`) — with the `PushSink`/`PushPayload` types owned by `internal/remote/relay/push.go:69-146`. The gateway becomes the owner of that seam; the relay's copy is deleted rather than left as a type nobody implements. B10's rename rationale ("the seam is renamed transport-neutral (`PushSink`/`PushPayload`) rather than keeping the APNs name for an FCM backend", `ADR-007:942-944`) applies again, in the other direction: the new home must not be named for FCM either.

**P3. Play-Store Android is the first client. iOS/APNs is not the active target.** This amends the 2026-07-23 amendment item 1 (`ADR-007:286-296`) and the surviving half of D12 (`:94`). "Not the active target" is the precise claim: no APNs vocabulary remains in a normative or operational document, no Apple-account dependency gates any wave, and the D12 Xcode/device gate is dormant rather than deleted. The gomobile-bind-safe phone-core surface that the 2026-07-23 amendment justified by the two-binding argument is **kept** on its own merits — it is the seam Android binds through today — and this ADR does not license anyone to "simplify" the core by putting an unbindable type on the boundary now that only one binding exists.

**P4. The push gateway is a small versioned HTTPS service that Swarm operates, and a named party in the adversary set.** Its shape is fixed before its threat position is: "a small versioned HTTPS service with five logical operations" (playbook `:514`, the operation table at `:516-522`), whose first required control is "TLS, strict request/body limits, fixed or padded wake shapes, per-address and per-source quotas" (`:526`). Two halves of that control line are stated here because no other ruling in this document carries them. **Transport is TLS only**, on the ordinary Web PKI that ADR-016 (Web-PKI relay TLS) makes the default *for the relay* — ADR-016's scope is relay TLS policy (RC-D10, playbook `:80`) and it makes no claim about gateway TLS, so this is a parallel ruling reached the same way rather than an inherited one. The gateway is a public Swarm-operated host, so it has none of the self-hosted relay's certificate-provisioning excuses. **Requests and bodies are bounded before parsing**, because every gateway operation is reachable by an unauthenticated caller at least as far as its size check, and the component behind that check is the only background wake path B16 left. **The API is versioned**, which is a decision-record property rather than an implementation taste: it is what makes P12's compatibility window expressible at all — an old installation and a new gateway must be able to name the same contract — and it is what R1's OpenAPI obligation is written against. B133's boundary (`ADR-007:7772-7773`) lists four in-scope items: the relay, the network path, FCM/Google, and any MITM that can position itself between the two endpoints. **The Swarm push gateway is added as a fifth entry on that list**, and — reading "party" as an operator with a name and a contract rather than a position on the wire — it is the *fourth named party*, after the relay operator, Google, and whoever runs the network path; the MITM is a capability, not a party. The distinction is stated because the sentence is doing threat-model work: what makes the gateway new is not that it can observe traffic but that RC-D2 makes the relay operator a *different* party from Swarm, so the security review's obligation is the colluding pair, not each in isolation. Playbook §11.3 requires that "a colluding compromised relay and push gateway still cannot decrypt content or forge a command" (`:918`). What the gateway may observe is fixed and disclosed: opaque push address, submit-source IP, timing, fixed or padded wake size, and the FCM outcome (playbook §5, `:351`). What it may not do follows from the keys it does not hold: it never receives a relay URL, relay-auth key, pairing secret, content key, device command key, daemon credential, or the wake key (P7). A compromised gateway may spam, suppress or correlate wakes; it cannot mint a wake authenticator, submit a command, or read a conversation (playbook `:355-359`).

**P5. Installation identity is a Keystore key and an opaque id; token rotation is deliberately independent of every machine pairing; Play Integrity is an abuse signal, never an account.** Registration exchanges an FCM token plus a Keystore-generated installation public key for an opaque installation id and allocates no machine address (playbook `:518`). Installation-control requests — token rotation, address allocation, address revocation — are signed over method, path, body hash, nonce and expiry (`:529-530`).

The rotate-token operation's defining property is the reason installation identity exists as a separate object at all: "**Replace the FCM token without changing every machine pairing**" (playbook `:520`). An FCM token rotates on the provider's schedule — reinstall, restore, app data clear, Google's own refresh — and a topology that bound the token to each pairing would turn every rotation into N re-pairings, each requiring the machine's confirmation. Splitting *who the handset is* (installation id, Keystore key, one token) from *where a given machine may wake it* (per-pairing address and capabilities, P6) is what makes rotation a single authenticated write with no pairing state touched. Do not "simplify" the two objects into one.

Play Integrity/App Check is required as a Play-app authenticity and abuse signal before public availability "but must not become an identity account" (`:560-561`); a device that fails attestation is refused registration or degraded to foreground-only, never enrolled into a durable identity. Debug builds use a separate non-production gateway and Firebase project (`:561`), so no test handset can spend or poison production quota. RC-D3's accountless product (`:73`) is unweakened: an installation id is a routing handle with a 180-day inactivity expiry, not a user.

**P6. A per-machine allocation is `{push_address, submit_capability, machine_revoke_capability}`; revocation is whole-address; and the two revocation paths belong to two different parties holding two different credentials.** Allocation is authenticated by the installation key and returns the triple exactly once for one pending pairing; the submit capability is not shown again and is reusable until the whole address is revoked (playbook `:519`). Submit and machine-revoke capabilities are distinct, stored only as hashed verifiers, and absent from logs and traces (`:527-529`, `:531`, `:922`). **An unbound allocation expires after ten minutes in every case** — abandoned pairing, failed SAS, crashed app — and a failed pairing deletes it immediately (`:136-139`, `:979`). Suspected capability exposure revokes the complete old address, allocates fresh capabilities, and rebinds through an authenticated pairing-update: **there is no in-place verifier swap**, because a swap leaves both generations momentarily usable (`:137-139`).

The two revocation paths are not two routes to one operation, and the copy must not blur them any more than playbook §4.9 does:

- **Phone-side removal ("forget this computer") revokes with the installation credential** (playbook `:146`). The phone still holds the installation key, so it can delete an address whose capabilities it may have already discarded. Force-forget retains only a bounded opaque deletion tombstone under that same installation key until success or the 180-day expiry (`:319-324`).
- **Machine-side revocation ("revoke this phone") uses the machine-revoke capability, and "retries deletion durably after local epoch rotation"** (playbook `:147`). The ordering is load-bearing and is the same ordering §4.9 gives for relay cleanup: local authorization is rotated and removed **first**, then the gateway deletion is retried durably; local authorization is never restored because an untrusted service is offline (`:325-327`).

That durable-retry-after-rotation clause is exactly the ADR-011 M5 edge. M5 makes a revoke rotate the epoch and makes epoch rotation a gateway-exit condition in its own right, so the process that owes the gateway a deletion is a process that is about to exit and restart. The obligation must therefore be persisted before the rotation and re-driven after the restart, in the same shape as P9's wake obligation — not held in the memory of a `swarm-remote` that M5 guarantees will not survive to send it.

**P7. The wake key is phone-generated, conveyed inside the authenticated pairing transcript, and never reaches the gateway — and this is a stated custody change, not an inherited one.** Today the wake key is machine-side epoch material: `machineid` mints it with the epoch keys and `cmd/swarm-remote/config.go:203` hands `id.EpochKeys().WakeKey` to the gateway params (`internal/remotegw/service.go:30-36`, `:183-186`). Under this ADR the phone generates it per machine pairing and transfers it — with the address, submit capability and machine-revoke capability — inside the pairing exchange; the machine persists all four before confirming pairing (playbook `:140-142`).

What that buys, stated so nobody "restores" the epoch derivation: the wake key stops being epoch-scoped, so an ADR-011 M5 epoch rotation no longer invalidates a push binding, and a push-address rotation no longer implies a content-key rotation. The two lifecycles are deliberately independent — which is also what makes P6's durable deletion retry *possible*, since the capability it retries with does not change under the rotation that interrupted it. **B19's actual requirement is untouched** — the push path holds the wake key *only*, no content key is in scope where a wake is built (`ADR-007:1237-1274`) — and `PushConfig`'s deliberate absence of an `EpochKeys` field (`internal/remotegw/push.go:43-67`) stays exactly as written, including `TestPBPUSH0_PushConfigCarriesNoContentKey` (`internal/remotegw/push_trigger_test.go:478`), which reads those fields reflectively and fails if the struct is widened "for convenience".

**That is a rule about content keys, and it does not freeze the struct.** `PushConfig` is edited by P8 delta 2 in the opposite direction: `EpochID uint32` (`internal/remotegw/push.go:57`) is **removed**, not retained, and the wake's routing coordinate becomes the per-pairing `PushAddress` P6 allocates. The wake key's *provenance* also moves off the epoch — `cmd/swarm-remote/config.go:203` hands `id.EpochKeys().WakeKey` into the gateway params (`internal/remotegw/service.go:30-36`, `:183-186`) today, and under this ADR the same field is loaded from the pairing record instead. An implementer who reads the paragraph above as licence to keep stamping an epoch id has read it as a freeze; it is a floor on what the struct may not gain, not a ceiling on what it may lose. **On `crypto.EpochKeys` specifically, so the two R1 records are not read as disagreeing**: ADR-018 MM1 freezes it as "`EpochKeys` stays the two-field wake/content split" (`ADR-018:47`), and that freeze is a ruling about the *machine-side single-device epoch shape* — it forbids adding a `RootKey` or a per-device `K_in,d` to it, and it says nothing about where the push path's wake key comes from. P7 removes the *use* of `id.EpochKeys().WakeKey` as the push path's source, not the field, and whether the now-unused field is finally deleted is R3's call under this ADR rather than something MM1 forbids. What MM1 does forbid, and what nothing here asks for, is a widened `EpochKeys`.

**P8. `WakeV1` is a new versioned wake shape, not the mailbox header reused. It keeps B10's payload discipline and every B20 property except the header layout, which it amends; three deltas are named here and nothing else in B10 or B20 moves.** The envelope carries only version, opaque push address, monotonically increasing per-machine wake sequence, issued-at, a five-minute expiry (**derived, not carried** — see the shape paragraph below), nonce, and an AEAD authenticator over **empty** plaintext under the wake key. Canonical AAD is the domain-separated tuple `(swarm-wake-v1, version, push_address, wake_seq, issued_at, expires_at, nonce)`, with the nonce unique under the wake key (playbook `:535-542`). It carries no session, interaction, cursor, provider, category, repository, prompt, tool or approval locator, **even encrypted** (`:543-544`, `:1024`) — B10's "must not carry session names, hostnames, agent names or Group labels" (`ADR-007:940`) restated with the locator ban made explicit.

**Why this cannot be the current envelope with fields renamed, which is the shortcut this paragraph exists to close.** `crypto.EnvelopeHeader.aad()` deliberately **excludes** `recipient_key_id` — "the header EXCLUDING recipient_key_id and the nonce" (`internal/remote/crypto/envelope.go:58-68`), excluded so one ciphertext fans out byte-identically to every recipient under A5 (`:43-47`). Any design that parks the push address in those reserved key-id bytes therefore leaves half the address **outside** the authenticator, mutable by relay, gateway or provider without breaking the tag — and an unauthenticated address selects which high-water coordinate delta 2 compares against, which is the pin-the-window lever `wake.go:87-95` exists to deny. The playbook forecloses it directly: `push_address` is inside the canonical AAD tuple and "the phone verifies the tag before trusting any header field" (playbook `:538-540`). The tuple is in any case not `aad()` by any reading — it adds a domain-separation string and `expires_at`, and it binds the nonce, which `aad()` deliberately omits because it is the AEAD's own parameter. So the wake's AAD changes, and this ADR says so instead of claiming an inheritance it does not have.

**The shape, stated concretely enough to be pinned.** `WakeV1` is a **74-byte** wire object: a 34-byte cleartext header — version (1), type (1), `push_address` (16), `wake_seq` (8), `issued_at` (8) — plus the 24-byte XChaCha nonce and a 16-byte AEAD tag over an empty plaintext. The type byte is a **new value, distinct from `TypeMailbox` 0x01 and the legacy `TypePushWake` 0x02** (`internal/remote/crypto/envelope.go:15-19`), so a parser separates the three shapes before it touches an AEAD, exactly as `OpenWake` refuses a type-0x01 envelope today; the domain string `swarm-wake-v1` in the AAD is the second, cryptographic half of that separation and is not a substitute for the first. `expires_at` is **derived**, not carried: it is `issued_at` plus the fixed five minutes of delta 3, computed identically by both sides and bound in the AAD, which is why it authenticates without costing a wire field or offering a field to mutate. **That is a deliberate deviation from the playbook's wording and is recorded as one rather than glossed:** playbook `:535-536` says `WakeV1` "carries only version, opaque push address, monotonically increasing per-machine wake sequence, issued-at, five-minute expiry, nonce, and an AEAD authenticator over empty plaintext". This ADR keeps every item of that list on the wire except `expires_at`. Nothing in the playbook's canonical AAD tuple changes — `expires_at` is still bound, and both sides compute the same value — and the deviation only narrows the attack surface, because a bound with no wire representation is a bound no party on the path can move. If the owner prefers it carried, the pinned size becomes 82 rather than 74 and this sentence is the thing to amend. Every byte on the wire is AAD-covered; unlike the mailbox header there is no excluded field, because there are no key ids to exclude. `WakeV1` is added **beside** the frozen mailbox envelope, never by editing it: `EnvelopeHeader`, `aad()`, `SealMailbox`/`OpenMailbox` and the type-0x01 wire bytes are not touched, and whether the new sealer/opener lands as a new constructor in `internal/remote/crypto` or in a package beside it is R3's call, constrained only by that rule. The legacy 78-byte type-0x02 wake is not mutated in place either — it is what a `legacy_relay` pairing keeps until P12 migrates it, and it retires with that transport.

The three deltas, each a consequence of P6/P7 rather than a new opinion. Each names the producer code and the receiver code it amends, not only the prose — the producer half is `(*PushNotifier).sealWake` (`internal/remotegw/push.go:484-500`) and the receiver half is `(*Core).AcceptWake` (`internal/phonecore/wake.go:104-148`), and two of the three land on both:

1. **The wake gets its own header. The opaque push address replaces the epoch id as the routing coordinate, and the two key-id fields cease to exist rather than being repurposed.** `crypto.EnvelopeHeader` reserves eight bytes each for `RecipientKeyID` and `SenderKeyID` (`internal/remote/crypto/envelope.go:43-56`); the wake path leaves both zero at the producer — `sealWake` stamps the header at `push.go:489-495` with the comment "RecipientKeyID and SenderKeyID stay ZERO. See above." at `:494`, and the "above" is the paragraph at `:470-477` arguing that reusing them would hand the provider "two stable identifiers linking every wake to one machine/device pair for the life of the epoch" (B20, `ADR-007:1275-1306`, and PB-PUSH-3's acceptance criterion at `docs/specifications/remote-phaseB-requirements.md:551`). Under `WakeV1` that whole paragraph and its comment are **deleted as obsolete rather than retargeted**: `sealWake` stops constructing a `crypto.EnvelopeHeader` at all and builds the 74-byte `WakeV1` header from the pairing's `push_address`, and `AcceptWake`'s `crypto.ParseEnvelope`/`crypto.OpenWake` pair (`wake.go:105`, `:134`) becomes the `WakeV1` parse/open pair. There are no key-id fields left to zero, so B20's "key ids zeroed" clause has no subject on the new shape.

   **The disclosure widens, and B77's honesty rule (`ADR-007:1835-1836`) requires the widening in the same breath as the design.** The push address is a stable identifier of exactly the machine/device pair B20's zeroing withheld — and P7 makes it *more* stable than what was withheld, because it is not epoch-scoped, so a revoke no longer rotates it (only P6's whole-address revocation does). It is in the payload, so both the gateway and FCM read it — which the playbook's own trust table already concedes for Google ("opaque address, clear wake counter/time", `:352`) and for the gateway (`:351`), and which nothing in ADR-007 concedes, because under B20 there was no address to concede. Concretely: under ADR-018's N machine pairings, one handset presents N distinct addresses converging on **one** FCM token, which lets either party count that handset's machines and separate their wake streams from each other — an inference the token alone did not support, since the token is one value for all N. ADR-018 reasons about the analogous relay-side correlation explicitly and reaches the same verdict (`ADR-018:123`: two routing ids behind one handset let a shared relay infer co-ownership, "a designed disclosure, not an incident"). The difference from that case is the one ADR-018 itself draws: the relay is the operator's own service, and the gateway is Swarm's. What is *not* conceded: the address is opaque and gateway-minted, it names no machine the provider can otherwise resolve, no endpoint **key id** or public-key-derived identifier is in the clear, the plaintext is still empty, and the size is still one pinned constant. The price is paid because the gateway cannot route without it, and paying it in an AAD-covered field is strictly better than paying it in a mutable one.
2. **The epoch id leaves the wake coordinate.** The replay guard becomes a per-`push_address` high-water, atomically persisted by the phone **before** routing (playbook `:540`, with the durable replay-check obligation restated at `:545`), rather than the per-epoch rule the phone enforces today. This follows from P7: a wake key that is no longer epoch material cannot carry an epoch coordinate that means anything. **On the producer** it deletes the `EpochID uint32` field of `PushConfig` (`internal/remotegw/push.go:57`, documented as "the epoch the wake key belongs to") and the `EpochID: n.cfg.EpochID` stamp inside `sealWake` (`push.go:491`), replacing both with the pairing's `push_address`; leaving that stamp in place while re-keying the phone's coordinate is the specific half-migration this clause exists to forbid, because it ships a machine authenticating a field no receiver reads. **On the receiver** it deletes step 2 of `AcceptWake`'s documented five-step order — "require the wake to name the epoch this phone holds a key for" (`internal/phonecore/wake.go:64-73`, implemented at `:130-133`) — and that step is defended in place at length under the heading "STEP 2 IS NOT REDUNDANT WITH THE TAG, which is the reading that leaves it out" (`wake.go:87-95`). That argument is not being overturned; its premise is being removed. It rests on "The wake key is per epoch and a revoke rotates it" (`wake.go:90`), which P7 makes false. The property it protected — a stale-generation wake carrying a high seq cannot pin the window — is preserved by P6's whole-address revocation instead: a revoked address is deleted at the gateway and its successor is a *different* `push_address` with its own high-water, so no coordinate is shared across generations for a stale wake to pin. `State.WakeReplay`, today one scalar because there is one epoch, becomes one coordinate keyed by `push_address`; with ADR-018's N pairings that is a table, and one machine's wake must never advance another machine's coordinate. The keyless arm at `wake.go:127-129` keeps its position and its verdict; what it tests becomes the per-pairing wake key P7 delivers.
3. **The expiry narrows from ten minutes to five.** B10 fixes the sealed wake as carrying "a persisted replay coordinate and a 10-minute expiry" (`ADR-007:939-940`); `WakeV1` carries a five-minute expiry (playbook `:536`), matching the five-minute FCM TTL the same document sets for the high-priority data wake (`:303`). **This is a real amendment and is stated rather than inherited**, and it is the one number in this ADR that a reader could otherwise assume was inherited from somewhere. It is not only ADR-007 prose: B77 rests on it in as many words — "its 10-minute replay window depends on it" (`ADR-007:1840`) — and the ten minutes is *also* shipped as a named constant with tests behind it, `const WakeMaxAge = 10 * time.Minute` (`internal/phonecore/wake.go:34-42`), whose comment argues the bound is load-bearing rather than a freshness nicety: "The seq window alone cannot express it: a relay that captures wake seq N and holds it while the gateway is quiet can deliver it days later, and seq N is still the highest the phone has seen." The code this delta amends is that constant and nothing else on the receiver — `AcceptWake` reads it at `wake.go:142` and the comparison itself is unchanged — so R3 changes the constant's value and re-runs its tests; the reasoning above it (`wake.go:34-41`) survives verbatim at five minutes, because narrowing the bound strengthens exactly the property the comment defends. On the producer the delta adds something rather than changing it: `sealWake` stamps only `issued_at` today (`push.go:493`), and under `WakeV1` the same call derives `expires_at` from it and binds both in the AAD, so the bound is authenticated at the sender instead of existing only as a receiver-side constant. The rationale is that an expiry longer than the TTL is a replay window with no delivery behind it: FCM will not deliver the message after the TTL, so the extra five minutes buy nothing and only widen the window in which a captured envelope is still nominally valid. The persisted counter B77 protects is **unchanged** — it is what actually rejects a replay; the expiry is only the outer bound, and this delta narrows that bound rather than widening it, which is the direction a security property may move without a second review.

The three refusals `AcceptWake` returns — `ErrWakeReplay`, `ErrWakeExpired`, `ErrNoWakeKey` (`internal/phonecore/wake.go:44-61`) — are **re-targeted by these deltas, not removed**. Replay and expiry keep their identities against the new coordinate and the new bound. `ErrNoWakeKey`'s deliberately separate identity from an AEAD failure — the two "are indistinguishable from the bytes and have opposite remedies", and the case it names is "a phone paired minutes ago and backgrounded before its first grant landed" (`wake.go:51-61`) — re-anchors on the per-pairing wake key P7 delivers inside the pairing transcript. That is still a reachable state, and its verdict must still be "waiting", never "invalid request".

`PushWakeEnvelopeSize` (`internal/remotegw/push.go:20-29`) survives as a pinned constant and **its value moves from 78 to 74**, which is a consequence of delta 1 rather than a free choice: `WakeV1`'s 34 field bytes plus the 24-byte nonce plus the 16-byte tag, against the mailbox header's 38 field bytes plus the same nonce and tag (`headerLen` = 62 counts fields and nonce together, `internal/remote/crypto/envelope.go:21-24`). The constant's doc comment argues that a conceded size disclosure "is benign only while it is CONSTANT" (`push.go:23-28`); that argument is untouched, and this is a one-time move of the pin, not a licence for the size to depend on anything. **The invariant is that there is exactly one constant with schema tests that fail when it moves — and that the number is derivable from the published schema, so a reviewer can recompute it rather than trust it.** Those tests are `TestPBPUSH3_WakeEnvelopeIsExactlyTheFixedContentFreeSize` (`internal/remotegw/push_trigger_test.go:503`) on the producer side and `TestPBPUSH3_AnUnschemadTriggerEnvelopeIsTheSameSizeOnTheChannel` (`internal/remote/relay/pbpush3_channel_test.go:504`) on the channel side; the argument for why the two must be pinned to each other by test rather than by the compiler is at `internal/remote/relay/push.go:34-38`, and R3 re-hosts that pinning against the gateway rather than the relay.

**P9. `swarm-remote` submits the wake directly to the gateway, under a durable coalescible obligation; the relay is not in the push path at all.** Before or atomically with mailbox publication, `swarm-remote` durably records a wake obligation keyed `(push_address, wake_seq)` (playbook `:550-556`). The gateway has **no hidden delivery queue**: it returns success only after FCM accepts the byte-identical request; timeout, transport failure, non-2xx and non-final FCM responses leave the obligation retryable; a response lost after FCM acceptance may duplicate, which the authenticator and high-water reject harmlessly; restart retries the byte-identical wake until success or declared expiry. Failure never rolls back or hides the published mailbox event, and FCM acceptance still does not prove handset display (`:548`).

Everything `PushNotifier` already decides is kept and now feeds the obligation instead of a relay op: the append-then-wake ordering and the rule that a failed wake never fails a record (`push.go:180-198`); the 30 s per-session coalescing window (`push.go:14-18`), pinned by `TestPBPUSH0_CoalescesRepeatTransitionsWithinTheWindow` (named at `push.go:340`, defined at `push_trigger_test.go:399`), which R3 must keep green against the new submitter rather than re-derive; the deferred-wake timer that re-reads the preference at send (`push.go:329-359`); the seeded-roster rule that stops a gateway restart firing n stale wakes (`push.go:156-178`); sender-side preference suppression, fail-closed on doubt (`push.go:443-466`); and the durable seq source, without which the phone's persisted replay coordinate rejects every wake after the first (`push.go:481-500`). The `PushTriggerer` interface (`push.go:36-41`) is re-pointed at the gateway client; the coalescing and category logic above it is not re-litigated.

**P10. The relay's second push producer is deleted, not ported — which discharges the residual `silentWakeCover` names, and only that one.** State the history in the past tense, because the repository has moved: B70-H2 measured `SweepPresence` driving unbounded high-priority wakes because `pushRate` guarded only `handlePushTrigger` (`ADR-007:3651-3655`), and B70-Q1's second bullet (`:3665-3672`), restated by B77 (`:1841-1848`), measured a keyless size separation letting the provider distinguish "a session changed state" from "this machine went offline". **Both were fixed in the relay before this ADR was written**: the sweep is charged against the same window as the trigger (`server.go:1754-1774`), the trigger refuses any envelope that is not 78 bytes (`server.go:1230-1232`), and the sweep carries `PushEnvelopeSize` random bytes so it separates on neither size nor content (`internal/remote/relay/push.go:41-67`). Nothing below may be cited as closing them.

What survives, and what this ADR closes, is the residual that fix could not reach: "a provider that PARSES rather than measures can still tell a wake from this. Closing that needs either a key the relay must not hold or dropping the sweep's push entirely, and both are decisions above this seam" (`internal/remote/relay/push.go:56-60`). A genuine wake's envelope header is cleartext — version, type, epoch id, seq, issued-at — and random cover bytes are not that, so a parsing provider still separates the two producers. P1 takes the branch the comment offers: the relay holds no push credential, so it has no producer at all, and the surviving single producer is `swarm-remote`, charged against the gateway's per-address and per-source quotas (playbook `:526`). The residual closes by removal of its subject, not by a new fence.

**The cost is real and is not disguised.** D9's "machine went silent" wake on gateway drop, with laptop sleep as a first-class phone state (`ADR-007:78`, N-7), loses its transport: the party that observes the drop is the relay, and the relay no longer has a way to tell the handset. The phone learns of machine silence on foreground reconciliation and from the connection states playbook §4.8 defines, which is why that section allows "machine asleep" to be inferred "only from authenticated presence/liveness evidence, not from a generic timeout alone" (`:298-299`). Restoring a silence wake later requires a submitter that is awake when the machine is not, and this ADR does not design one.

**P11. Token custody and the disclosure move with the credential.** B32 named the relay's stored token "a **join key between two parties whose views are otherwise disjoint**" (`ADR-007:1823-1830`). After this ADR the self-hosted relay holds **no provider-issued device identifier at all** — a real reduction for every relay operator, who is not Swarm — and the join key exists at the gateway instead, alongside the installation public key, opaque address, hashed capability verifiers, creation/last-use timestamps and minimum delivery diagnostics (playbook `:527-528`). FCM tokens are encrypted at rest and excluded from logs and traces (`:531`).

B77's honesty rule binds the new topology unchanged: **claim no less exposure than exists**. The cleartext, keyless-readable fields of a wake — address, counter, issued-at, and size — are disclosed as such, and "a token plus wake timing is an **activity trace**. The content is hidden; the rhythm is not" (`ADR-007:1852-1853`) remains true with the token now held by Swarm. P8 delta 1 adds one field to that cleartext list — the push address — and the widening it buys the gateway and the provider is stated there rather than left to this paragraph.

`docs/operations/metadata-disclosure.md` is the operator-facing form B32 requires not to diverge (`ADR-007:1856`), and it owes exactly three edits — no more, and specifically **not** an APNs correction, because that document has none to make: its §2 is already titled "The push provider (Google, via FCM v1)" (`:70`) and the Apple sentence exists only in D11 (`ADR-007:88`), which P3 amends there.

1. **Add the gateway as a third observing party**, beside §1 (the relay) and §2 (the provider), with the playbook §5 row as its content (`:351`). P8 delta 1's cleartext push address is disclosed inside *this* edit rather than as a fourth one, and the same edit corrects §2: the playbook's FCM row already concedes "opaque address, clear wake counter/time" to Google (`:352`), which is what B20's zeroed key ids did not concede and what §2 does not yet say.
2. **Add the gateway's submit-source IP.** This is a genuinely new observation and has no antecedent in the relay-hosted design: the submitter is now `swarm-remote`, so the party that sees the source address sees the *developer's machine*, not the handset. Nothing in the current document discloses a machine-side network identifier to anyone but the relay.
3. **Retarget §1a's join-key entry** (`:44-51`), which today reads as three bullets about the relay holding a provider-issued device identifier keyed by routing id. After this ADR the relay holds none; the same three properties — not encrypted, correlatable, the same identifier the provider holds — become true of the gateway, against the opaque push address rather than the routing id. This is a rewrite of the subject, not a deletion of the finding, and the auditability caveat in the same section ("that is an auditability property, not a confidentiality one") travels with it.

Retention is published **before the first real token is collected** (playbook `:534`), with §13's periods as product behavior: ten minutes for an unbound allocation, seven days for delivery diagnostics, 180 days for an inactive installation mapping (`:979-981`).

**P12. Migration is one `push_transport` per pairing, one compatibility window, and one honest degraded state.** Each pairing persists exactly one of `legacy_relay`, `gateway`, `foreground_only`. A machine leaves `legacy_relay` only after Android gateway registration, address allocation, authenticated pairing-update acknowledgement, **and a successful gateway test wake**; the transition is atomic and rollback selects one transport, never both (playbook `:955-962`). During the window revocation attempts both legacy and gateway deletion idempotently, while the wake sequence and the selected state forbid double delivery. A user may disable the gateway, and the app must then say "foreground updates only" and must not imply reliable background delivery (`:148-149`); a disabled or unreachable gateway is a visible degraded state in Settings and machine health (`:313`), sitting beside — not replacing — B143's unconditional Doze/battery-saver sentence (`ADR-007:8599-8602`).

### Invariants that do not change — listed so no implementer "fixes" one on the way past

- **E2EE and signed commands, not network separation, are what prevent content access and command forgery** (RC-D7, playbook `:77`; `:355-359`). The gateway split is a credential-custody decision. It is not a security mechanism and must not be described as one.
- **B16's ruling stands**: backgrounding disconnects, no foreground service, high-priority FCM is the sole background wake path, and push is load-bearing (`ADR-007:1111-1160`). This ADR changes who sends the wake, not whether the socket is held.
- **B10 minus P8's three deltas**: fires on the transitions an owner is waiting on, 30 s per-session coalescing, content-free plaintext, data-only so the app decides the notification, no session names or hostnames or agent names or Group labels, and a real device→machine preference verb whose suppression is machine-authoritative (`ADR-007:928-950`). Only the submitter, the transport, and the three named deltas change.
- **B19's push-path key inventory**: wake key only, no content key in scope where a wake is built (`ADR-007:1237-1274`), enforced by `PushConfig`'s shape and by `TestPBPUSH0_PushConfigCarriesNoContentKey` (`internal/remotegw/push_trigger_test.go:478`).
- **The phone authenticates before it compares, and persists only after it accepts.** "The phone verifies the tag before trusting any header field and atomically persists the accepted per-address high-water before routing" (playbook `:539-540`); `AcceptWake` already implements that ordering and defends it: "Steps 3-before-4 is the part that is easy to get backwards and expensive to get wrong. A receiver that advanced the coordinate before authenticating would hand the relay a one-packet permanent denial of service: an unopenable envelope carrying seq 2^63 pins the window at the top and every genuine wake afterwards is refused as a replay" (`internal/phonecore/wake.go:67-79`, with the "AUTHENTICATED from here down" fence at `:137-138`). **This is the invariant most at risk from P8**, because P8 replaces the epoch check and re-keys the coordinate inside exactly that function: re-plumbing around the ordering is the plausible accident, and it is not licensed here. The address is a routing field like the epoch id was — it selects which coordinate to compare against, and comparing is still step 4. It is **fully AAD-covered** under P8 delta 1's `WakeV1`, which is the property that makes selecting on it safe at all; an address read from bytes outside the authenticator would let any party on the path choose the victim coordinate, which is why delta 1 is a new shape rather than a reuse of the mailbox header's excluded key-id bytes.
- **B20's shape discipline, minus the one thing P8 delta 1 amends**: no endpoint key ids in the clear, exactly one pinned constant size, empty plaintext, a durable replay coordinate (`ADR-007:1275-1306`), fenced by `TestPBPUSH3_WakeEnvelopeIsExactlyTheFixedContentFreeSize` and `TestPBPUSH3_AnUnschemadTriggerEnvelopeIsTheSameSizeOnTheChannel`. **Read this row with delta 1, never alone**: the header layout is amended, the pinned size moves from 78 to 74, and `WakeV1` carries the opaque `push_address` in the clear. That is a **stable per-pairing identifier of the machine/device pair** which the zeroed key ids withheld and which P7 makes more stable than they were, since it survives epoch rotation; with ADR-018's N pairings, N addresses against one FCM token let the gateway and FCM count and separate one handset's machines. B20's remaining properties are unchanged, and the disclosure is conceded rather than argued away.
- **B143's disclosure**: the fixed Settings sentence about Doze and battery saver stays, unreworded, and stays out of the conditional-notice list (`ADR-007:8581-8612`).
- **The relay stays untrusted, ciphertext-only, and self-hosted** (RC-D2, RC-D7). Removing push from it makes it smaller, never smarter. Its presence tracking, `SweepPresence` transition bookkeeping and `pushRate` quota shape are not otherwise disturbed by P10 — only the delivery call at `server.go:1783` and what feeds it.
- **ADR-011 is not partially implemented here.** One phone with N machine pairings gets N independent addresses, wake keys and capabilities (playbook `:482-487`); `Registry.AddSole` is not weakened and multiple phones per machine stay refused until every ADR-011 milestone lands together (`:165-170`). ADR-018 governs that split; this ADR only guarantees the push objects are per-pairing so they never become the reason someone reaches for a shared one.
- **No account.** RC-D3 (`:73`) survives P5 intact.

## Consequences

### Positive

- The one blocker to distributing the app is removed at its root: no relay operator is ever asked to hold Swarm's Firebase sender credential, and D12's own trigger condition is discharged rather than restated.
- Every self-hosted relay loses a provider-issued, long-lived, device-specific identifier from its at-rest footprint — B32's join key is no longer in the operator's bbolt file, and the operator's threat surface shrinks without anyone auditing their deployment.
- The parsing-provider residual `silentWakeCover` records as unclosable from inside the relay (`internal/remote/relay/push.go:56-60`) closes by removing its subject, without adding a key the relay must not hold.
- The push path acquires exactly one producer, one shape and one quota domain, so the class of finding B70-Q1 belongs to — one fence pinning one producer while a second is structurally invisible to it — has no second producer left to hide in.
- `internal/remote/push` stops being "a perfectly-tested FCM sender that no binary ever installs" (`cmd/swarm-relay/main.go:66-68`) and acquires the one caller that can legitimately hold its credential.
- The push and content lifecycles decouple: an epoch rotation no longer disturbs a push binding, an address rotation no longer disturbs session keys (P7), and a provider token rotation no longer disturbs a single pairing (P5).
- The gateway is small enough to be reviewable in full — five operations, no session traffic, no relay knowledge — which is what makes "Swarm does not receive session traffic or plaintext wake content" (playbook `:1011-1012`) a checkable claim rather than a promise.

### Negative

- **Swarm now operates a production service with users' handsets behind it.** Availability, abuse handling, incident response for token or credential exposure, a published privacy notice, retention jobs and an appeal path are ongoing obligations (playbook `:1000-1009`), and B16 already made a dropped push a missed hand-off with no fallback. The product's background path now depends on a component the developer running a self-hosted relay does not control — a real dent in the self-host-first claim, which §14 must state plainly rather than around.
- **D9's "machine went silent" wake loses its transport** (P10). Laptop sleep stops being announced and becomes something the phone discovers on reconciliation.
- A new entry joins B133's adversary list, and the security review's obligation grows from "compromised relay" to "compromised relay **and** compromised gateway, colluding" (playbook `:918`).
- **The wake payload discloses one field more than B20 conceded.** `WakeV1` carries the opaque push address in the clear (P8 delta 1), where the old shape carried two zeroed key-id fields. The address is stable per pairing and, under P7, no longer rotated by an epoch change, so both the gateway and FCM can count and separate one handset's machines — N addresses against one token — which the token alone did not reveal. It is the price of routing through a party that must route, it is paid in an AAD-covered field rather than a mutable one, and it is disclosed here, in the invariant list, and in `metadata-disclosure.md` per P11 rather than argued away.
- The join key does not vanish, it moves: Swarm's gateway now holds an FCM token, a source IP that identifies the developer's machine, and wake timing for every installation — a correlation the previous topology spread across N independent operators. `metadata-disclosure.md` §1a becomes a statement about Swarm (P11).
- A compatibility window with two push transports, an atomic per-pairing state, and idempotent dual revocation is real migration cost (P12) for a legacy path that has never delivered a production wake.
- The machine-side revocation path now owes a durable obligation across an ADR-011 M5 process exit (P6), which is a second crash-consistent state machine beside P9's wake obligation, in the same component, with the same fault-injection bill.
- Play Integrity, a closed beta, and per-installation registration bounds are abuse controls a personal-only build never needed, and each is a place a legitimate user can be wrongly refused — hence the required appeal path.
- iOS moves from "first-class, later" to "not the active target", and every Apple-shaped artifact in the repository becomes dormant text that R1 must label rather than silently retain.

## Alternatives Considered

**The relay keeps the sender credential (the status quo, `config.go:57-64`).** Rejected: it is unshippable for a Play-signed app, and D12 said so before any of this was built — "relay cannot hold the APNs signing key if the app is ever distributed" (`ADR-007:94`). The deferral was granted on the personal-only premise, and that premise ends at the Play track. Distributing one application's sender credential to every relay operator would also make any operator able to push arbitrary high-priority wakes at any Swarm handset, which no quota on their own relay can bound.

**Per-operator Firebase projects — every self-hoster registers their own project and their own app.** Rejected on two independent grounds. It makes every operator a push administrator: a Google Cloud project, a service account, a rotation policy and a Play/Firebase console, in exchange for a wake that carries nothing. And it forks the application configuration — `google-services.json` is compiled into the APK for a specific package and sender (`android/app/google-services.json`, project `swarm-8404f`, sender `733314021126`), so per-operator projects mean per-operator builds, which is incompatible with one Play-signed artifact. A runtime-configurable `FirebaseOptions` variant survives the build objection but not the first: it still hands each operator the whole administrative burden and the ability to observe token, timing and size for the handsets that trust them.

**No push at all — foreground-only, and the socket policy is the whole answer.** Rejected: B16 already priced this and decided the other way, and its consequence line is explicit that push became load-bearing rather than a convenience (`ADR-007:1144-1146`). Without a wake, "the phone as a second surface" degrades to "the phone as a thing you remember to open", and playbook §4.8's entire notification contract disappears. `foreground_only` survives as a **user-chosen** state with honest copy (P12), which is the correct scope for the idea.

**Keep the relay as the push proxy, forwarding to the Swarm gateway.** Rejected: it buys nothing and costs the property the split exists for. The relay would still hold the token map (B32's join key stays in the operator's store), would still be a push producer (so `silentWakeCover`'s parsing residual stays open), and would still be the party able to drive wakes, while adding a hop and a second failure mode. The wake submitter must be the party that can authenticate the wake, and that is `swarm-remote`, which holds the wake key.

**Give the gateway the wake key so it can build or validate the envelope.** Rejected outright: it converts a blind forwarder into a party that can mint an authenticator, which is the one thing playbook §11.3 requires it never do (`:922`). The gateway forwards the envelope unchanged (`:145`); it does not parse, re-seal, or inspect it.

**Let the gateway hold a delivery queue and retry on the machine's behalf.** Rejected: a queue makes the gateway stateful about undelivered user activity, makes "success" mean something other than "FCM accepted", and duplicates a retry obligation `swarm-remote` must have anyway for the crash cases. The playbook's shape — success only after FCM accepts the byte-identical request, retry owned by the durable obligation on the machine (`:550-556`) — keeps the gateway minimal enough to justify P4's disclosure.

**Push-address per installation rather than per machine pairing.** Rejected: one address across N pairings makes the gateway able to correlate a developer's machines with each other, breaks per-machine revocation into an all-or-nothing operation, and gives one machine's leaked submit capability authority to wake on every other machine's behalf. Per-pairing allocation (P6) is also what keeps ADR-018's multi-machine model from needing a shared object — and it is the half of P5's split that must *not* be merged into installation identity, however tempting the symmetry looks.

**Bind the FCM token to each pairing and re-pair on rotation, dropping installation identity.** Rejected: it makes a provider-scheduled event into an N-way re-pairing ceremony requiring each machine's confirmation, which is precisely the property playbook `:520` names as the rotate-token operation's purpose. Token rotation is frequent and involuntary; pairing is rare and deliberate. Coupling them puts a user's background delivery at the mercy of how many machines they happen to have paired.

## Notes

Numbering: 015 was the next free number by `docs/adr/README.md`'s own count when Wave R1 was allocated — 013 is the Mirror capture architecture and `mirror-program.md` M3.1 reserved 014 for paged interaction history. This ADR is one of four minted together for playbook Wave R1 (016 Web-PKI relay TLS, 017 capability-driven terminal fallback, 018 multi-machine pairings); they were drafted concurrently and cross-reference each other by number and title only. The README's step 1 has since been advanced by the same change that landed these four files and now reads "the next FREE one is ADR-019" (`README:41`), with 014 still reserved.

An earlier draft of this document asserted that B70-H2 and B77's shape separation were open findings this ADR would close. They were not: both were fixed in the relay before it was written, and the code that fixed them names the fix in place (`server.go:1754-1774`, `internal/remote/relay/push.go:41-67`). The correction is preserved here rather than quietly applied, because "an old finding that the current code already closed" is the exact shape of claim a decision record can inflate without anyone noticing — and because the residual that *is* open (`push.go:56-60`) is a narrower and more honest thing to be discharging.

This ADR is otherwise written in the shape ADR-011 used for a decision recorded ahead of its implementation: the mechanism is decided, the invariants that must not be "fixed" are enumerated, and the evidence is current-code citation rather than measurement, because there is none to cite. Not one wake has left this repository toward Google. The most likely way for this document to become wrong is for R3's handset work to discover that FCM's real behavior — quota, Doze interaction, token rotation cadence, `UNREGISTERED` semantics against a Play-signed package — does not match what `internal/remote/push`'s tests assert against a loopback server. Playbook §16's closing rule governs that case: amend the decision record and the playbook in the same change, and do not preserve an attractive roadmap sentence over observed provider behavior.
