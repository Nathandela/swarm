# ADR-018: Multi-machine pairings — one phone, N independent single-device relationships

**Status**: Proposed (drafted 2026-08-14 from the owner-approved playbook; pending owner sign-off)
**Date**: 2026-08-14
**Source**: [docs/specifications/remote-control-product-playbook.md](../specifications/remote-control-product-playbook.md) RC-D8 (`:78`), §3.4 (`:165-170`), §4.2 (`:194-208`), §4.9 (`:315-334`), §6.4 (`:474-488`), §12 Android state (`:937-947`), wave R4 (`:751-766`), §11.2 (`:905-906`).
**Relates to**: [ADR-011](ADR-011-multi-device-epochs.md) (multi-**device** epochs) — this ADR adds a scope marker under its header block and an appended scope note at the end of it (MM9), and takes nothing from it. Nothing in ADR-011 is superseded, weakened, partially adopted, or brought forward.
**Companions**: ADR-015 push-gateway split (the per-machine wake address, submit capability and machine-revoke capability MM5 consumes), ADR-016 Web-PKI relay TLS (the per-pairing relay destination MM2 makes plural), ADR-017 capability-driven terminal fallback (the per-session capability record MM4's session identity keys).

## Context

### Two different words that have been used as one

ADR-011 is about **N devices on one machine**: N phones or tablets, one owner, one daemon, one epoch, one machine-side registry. Its whole content is the machine-side consequence of that — a nonzero per-device `SenderKeyID`, a per-device inbound key derived from a machine-only `RootKey`, per-device seq spaces, per-device grant counters, per-device reconcile authorities, a lease bound to the sender id that opened it, and an admin tier to govern who may revoke whom (`ADR-011-multi-device-epochs.md:35-65`).

This ADR is about **N machines on one phone**: N daemons, N pairings, one handset. RC-D8 states the split as a product decision — "Multi-machine is in the first complete product; multi-phone is later. Android state becomes a collection of independent machine pairings. The machine's current single-device enrollment limit remains until ADR-011 is implemented as one coherent program" (`remote-control-product-playbook.md:78`) — and §3.4 states it as an implementation constraint: "Record multi-machine as an Android/client-state change: one phone stores several independent machine pairings. Do not weaken `Registry.AddSole`, share inbound sequence spaces between phones, or partially implement ADR-011" (`:165-170`).

ADR-011's Context names the boundary it moves: with N devices, "each paired device is in scope as an adversary of its peers" (`ADR-011:27`). **This ADR moves no boundary at all.** N machines is N separate instances of the relationship v1 already ships: one machine, one phone, one epoch, one trusted holder. The holder is the same person holding the same handset in every one of them. There is no peer to attribute against, no peer to arbitrate a lease against, and no peer to revoke. That is why the machine-side design is untouched and why nothing in ADR-011 becomes cheaper, closer, or partially due.

### What "one phone, one machine" is actually made of today

Five things assume a single destination, and all five are on the **phone** side of the boundary:

1. **The bound facade's `Config` names one of everything.** `Config{StateDir, RelayURL, MachineID}` — "StateDir is the phone's private state directory (device keys plus the one durable state blob); RelayURL is the relay to dial; MachineID is the machine endpoint id whose durable coordinates this app resumes" (`mobile/types.go:21-29`). Three scalars, one destination.
2. **`App` holds those scalars and derives one relay mailbox from them.** `relayURL` and `stateDir` are `App` fields (`mobile/app.go:80-85`); `destination()` returns the single `(machineTarget, machinePub)` pair every append is routed to (`mobile/app.go:242-247`); `NewApp` resumes exactly one core with `phonecore.Config{Dir: cfg.StateDir, Machine: cfg.MachineID, ...}` (`mobile/app.go:199-202`, `internal/phonecore/core.go:44-51`).
3. **The durable blob is single-machine by construction, and enforces it destructively.** One `phone-state.json` per state directory at `StateSchemaVersion = 12` (`internal/phonecore/state.go:144`), whose `machine` field is a load-time filter: a blob whose machine does not match the configured id "is discarded wholesale" (`state.go:1252-1256`, and the reason it must stay readable before any unseal at `state.go:474-477`). `internal/phonecore/s9_machineid_test.go:1-26` pins what that costs when it fires wrongly — "discarding the pairing, the epoch, the sealed content key, the relay cursor and the durable send-seq ceilings. None of that is recoverable." Writing a second machine's coordinates into that blob does not add a machine; it deletes the first.
4. **Android caches exactly one `App` and remembers exactly one relay.** `PhoneRuntime.phone()` latches a single `PhoneStartup.Ready` under `@Synchronized`, because "two concurrent `NewApp` calls would give the same state directory two owners" (`android/app/src/main/kotlin/dev/swarm/phone/PhoneRuntime.kt:49-65`); `rememberRelay` writes one `RELAY_FILE` for the whole install (`:67-81`).
5. **Every read model the screens hold is scalar.** `StateSummary{Machine, EpochID, SendSeq, RelayCursor, ...}` (`mobile/types.go:394-403`), `MachinePresence{State, ObservedUnixMs}` (`:435-438`), `Freshness` (`:419-422`), and `Event.SessionID` with no machine field (`:50-58`).

None of those five is a crypto or protocol fact. Every one of them is client state. That is the entire reason multi-machine can ship first: it is a refactor of the phone's composition, and the machine never learns that another machine exists.

### Why record it now

Wave R4 exists to "remove singleton state before the final chat screens make it more expensive" (`playbook:753`), and waves R5-R8 build screens on top of it. The migration in §12 is one-way in practice (`playbook:937-947`), so the shape it migrates *into* has to be decided before it runs, not after three screens have taken a dependency on a scalar `App`.

## Decision

Rulings are numbered **MM1-MM9** and not M1-M9, deliberately: `M3` already means something in ADR-011 and the two must never be cited into each other.

**MM1. Multi-machine is an Android/client-state change. The machine-side single-device model is frozen, in full, by name.** No ruling below is permitted to weaken any of the following, and no implementer may "fix" one of them in passing:

| Frozen site | What stays |
|---|---|
| `internal/remote/device/registry.go:190-224` | `Registry.AddSole` stays, with its under-the-mutex refusal of a second device id and its idempotent same-device upsert. It is not renamed to `Enroll` and gains no sender-id or capability-tier argument. |
| `internal/skeleton/pairing.go:133-137` | `BeginPairing`'s fast-reject stays, including its remedy-naming error text ("a device is already paired (single-device v1); run `swarm remote devices` ... `swarm remote revoke <device-id>`"). |
| `cmd/swarm-remote/config.go:125-126` | `resolveGatewayParams` still refuses to start at `len(devices) != 1`. |
| `internal/phonecore/input.go:44-47`, `internal/phonecore/direction.go:57` | `SenderKeyID` stays **zero** inbound; one `Sequencer` per epoch, because commands and input frames share one `MailboxReceiver` key. |
| `internal/remote/crypto/epoch.go:41,44`; `crypto.EpochKeys` at `epoch.go:48-55`, `SealEpochGrant`/`OpenEpochGrant` at `epoch.go:93`/`:114` | No `RootKey`, no `K_in,d`; `EpochKeys` stays the two-field wake/content split — a freeze on the struct's *shape* against ADR-011's `RootKey`/`K_in,d` additions, not a ruling about where the push path's wake key comes from, which ADR-015 P7 (`ADR-015:70`) moves to the pairing record; `grantVersion` stays `0x01` and `grantInnerLen` stays `1 + 8 + 4 + 8 + 32 + 32` (85). |
| `internal/protocol/schema/reconcile.go:27-36` (`schema.ReconcileRecord`) | Stays scalar. No keyed per-device group. |
| `internal/remotegw/command_loop.go:65-68` (`LeaseRouter`) | `Begin(cmd protocol.RemoteCommand)` and `Input(session string, f InputFrame)` carry no sender id. Gateway exit stays on own-device deregistration alone. |

ADR-011 says why this table is all-or-nothing rather than a menu: "They are not separable ... Partial adoption is worse than none, and this paragraph exists so that a later reader does not take one of them in isolation" (`ADR-011:94`). Multi-machine does not need one of them, so it takes none of them. ADR-011's gate is unchanged and is still distribution-shaped: it fires "the moment a second device of the same owner is to be paired" (`ADR-011:94`), which shipping this ADR does not cause.

**MM2. The unit is a pairing, and `MachineClient` is one pairing entire.** Per `playbook:478-479`, a `MachineClient` owns "one pairing, key store, relay destination, cursors, read models, connection loop, command sequencer, and operation journal". Ruled explicitly, because "independent" has to be enumerated to be testable — each of these is **per-pairing and shared with nothing**:

- the device signing key and the recipient key, and their Keystore-wrapped custody;
- the epoch id and its content key — **epoch-scoped**, and rotated by an ADR-011 M5 revoke;
- the outbound send-seq space and its durable reservation ceiling, and the inbound high-water;
- the relay URL, the relay-auth public key, the derived routing id, and the read cursor;
- the folded read models — roster, journal, transcript, terminal snapshots — and their staleness sets;
- the operation-id space and the operation journal that resolves outcomes by it;
- the state directory namespace the whole lot is persisted under;
- the push address, the **pairing-scoped** wake key, the submit capability and the machine-revoke capability (MM5). The wake key is listed here and deliberately **not** beside the epoch's content key above: ADR-015 P7 (`ADR-015:70`) makes it phone-generated per machine pairing and conveyed inside the pairing transcript, so "the wake key stops being epoch-scoped" (`ADR-015:72`) and an epoch rotation does not invalidate it. There is one wake key per pairing, with one provenance; the epoch-scoped reading is the one this bullet exists to foreclose.

`playbook:485-486` is adopted verbatim as the negative half: "No content key, relay identity, cursor, operation id, or state directory is shared between machines." A `MachineClient` is constructible more than once in a process and holds no package-level state.

**MM3. `MachineManager` is the only plural object, and its concurrency policy is deterministic and visible.** It owns the durable registry of machine descriptors, lifecycle orchestration of the clients, one aggregate event stream, the foreground connection cap, and add/remove/select (`playbook:480-481`). Three properties are rulings rather than implementation detail:

- **The cap is documented and the overflow policy is deterministic least-recently-viewed** (`playbook:200-202`): "When foregrounded, the app connects to every paired machine within a documented concurrency cap ... Connections beyond the cap use a deterministic least-recently-viewed policy and visibly show their last-sync age."
- **Every event on the aggregate stream is machine-qualified.** `mobile.Event` (`mobile/types.go:50-58`) gains the machine id; a consumer that cannot say which pairing woke it cannot route it.
- **The UI reads immutable snapshots from the manager, not mutable singleton globals** (`playbook:574`). The `Stale`-on-the-handle precedent generalizes rather than being re-argued: staleness rides the object, because "a screen that has to remember to call `StreamState("journal")` beside every `Roster()` is a screen that will forget once, and the failure is silent and looks exactly like a working app" (`mobile/types.go:106-121`, and the stronger transcript case at `:316-328`). Per-machine last-sync age is the same class of fact and rides the same way.

**MM4. Session identity is always the tuple `(machine_id, session_id)`; a display title is never an authority.** `playbook:199` states it flatly — "Session identity is always `(machine_id, session_id)`; a display title is never an authority" — and this ADR makes it binding on every surface: the roster, the aggregate inbox, deep-links, operation records, caches, and every wire body that names a session. Two machines may legitimately serve the same session id and the same display title; R4's exit requires that "duplicate session ids and display names do not collide" (`playbook:765-766`) and §11.2's handset matrix runs it on real hardware (`playbook:905-906`). Per-session provider capability records (ADR-017) are keyed by the same tuple, since a session instance exists on exactly one machine.

**MM5. Push is one installation credential and N independent per-machine wake addresses.** `PushRegistration` holds "application-level installation credential plus one independent opaque wake address, wake key, submit capability, and machine-revoke capability per machine" (`playbook:482-483`); the credential and capability shapes belong to ADR-015 and are not restated here. Two consequences are this ADR's:

- A validated wake resolves **at most its opaque machine pairing** and nothing narrower; the authoritative session/interaction target comes from that pairing's own relay reconciliation, and "it never derives a session/card target from FCM data" (`playbook:203-206`). A missing target opens that machine's inbox with an honest explanation.
- Losing, disabling or degrading push for one pairing degrades that machine's row only. The degraded state is per-machine and visible (`playbook:313`).

**MM6. The migration from singleton state is atomic, verified-before-mutating, and rollback-readable for one release train.** §12's six steps are adopted as normative (`playbook:939-947`): read the existing singleton state and **verify custody before modifying anything**; create a registry entry keyed by the **authenticated** machine id (not the configured string, not the display name); move state into a per-machine namespace with keys remaining Keystore-wrapped; **commit the registry last**; on failure continue opening the old state read-only and offer retry; remove rollback compatibility only after at least one stable release train.

The prohibition in step 5 — "never produce two live send sequencers for one pairing" — is the load-bearing one and its cost is already recorded in this repo: the sequencer is durable precisely "so no seq is ever re-issued after a process death" (`internal/phonecore/input.go:48-50`), and a re-issued seq under a retained epoch is stale-dropped by the gateway permanently (`s9_machineid_test.go:16-19`). A migration that leaves the old singleton `App` running beside the new `MachineClient` for the same pairing is therefore not a cosmetic overlap; it is an unrecoverable pairing. Ordering follows from the same fact: the registry commits last so that a crash mid-migration leaves the old blob authoritative, and the old blob's machine filter (`state.go:1252-1256`) keeps discarding anything that is not its own — which is the behavior that makes step 5's read-only fallback safe rather than merely polite.

**MM7. Forget-a-computer and revoke-a-phone are different operations, and neither may reach a second pairing.** §4.9 is adopted as written (`playbook:315-334`), including the clauses that are easiest to drop:

- **Forget this computer on this phone** is phone-side (`playbook:319-324`). It "first revokes its push address with the installation key", then deletes that machine's keys and cache, after warning that the computer still authorizes the old device id and must revoke it before re-pairing. Gateway unavailability waits and retries by default. **Force forget** takes a second confirmation, deletes the machine secrets, and retains "only a bounded opaque deletion tombstone under the installation key until success or the gateway's 180-day expiry; the copy names the possible residual generic-notification window." Both the tombstone's bound and the residual-window copy are binding here; the gateway-side halves of them — tombstone storage, the 180-day expiry itself, and the installation-key revoke path — are ADR-015's to specify, not this ADR's to redefine.
- **Revoke this phone from this computer** is machine-side (`playbook:325-327`), is the existing single-device revoke, and is unchanged by this ADR. Its full shape is retained: it "first rotates/removes machine authorization and refuses future commands, then durably requests relay cleanup and push-address deletion. Partial cleanup is shown and retried; local authorization is not restored because an untrusted service is offline." Neither half is this ADR's to define. **Relay cleanup** is ADR-007 D9's existing "device de-authorization + mailbox purge on revocation (a revoked device keeps neither connectivity nor a drainable pre-rotation mailbox; an offline-at-revoke machine defers the purge to reconnect)" (`ADR-007-remote-access.md:78`, D9's "device de-authorization + mailbox purge on revocation"), restated as a release gate at `playbook:932-933`; it is not TLS policy and is therefore not ADR-016's. **Push-address deletion** is ADR-015's. What this ADR binds is only the plurality: both requests name exactly one pairing, and a partial-cleanup retry loop for machine A never touches machine B.
- **Phone lost or app reinstalled** is recovered from the computer with `swarm remote revoke` then a fresh pairing; "Re-pairing without revoking the old device is refused by the single-device registry" (`playbook:329-330`) — that refusal is MM1's `AddSole`/`BeginPairing` pair, and it stays.

The isolation rule is stated as its own sentence because a shared-storage optimization would silently break it: **one machine's removal or revocation cannot alter another pairing** (`playbook:334`). Epoch rotation on machine A rotates machine A's epoch; machine B's keys, cursors, seq spaces and push address are not read, not rewritten, and not invalidated. This is trivially true under MM2 and is stated anyway, because it stops being true the moment someone puts two pairings in one file.

**MM8. A fault is scoped to its pairing.** A corrupt or future-schema blob, a poisoned relay cursor, a disowned registration, a Keystore invalidation, an app upgrade or a process death degrades exactly the machine whose namespace it belongs to; the remaining pairings stay live and the aggregate inbox says which row is broken and how stale it is. Per-machine recovery screens are required, not optional (`playbook:575-576`). R4's exit is the test of this ruling: three machines — two on one organization relay, one on another — all live, one revoked in isolation, all three restored after process death (`playbook:763-766`).

**MM9. ADR-011 gains a scope marker and an appended scope note, and nothing else.** What lands in ADR-011 is a one-line marker directly under its header block pointing at the note, plus a short appended scope note at the end of the file stating that ADR-011 governs **multiple devices paired to one machine**, that multi-machine (this ADR) ships first, that it draws nothing from M1-M9, and that M1-M9 remain undue until a second device of the same owner is to be paired. The reciprocal note is added in ADR-011 itself by the R1 annotation pass; this ruling states the relationship, and the direction of the dependency: **ADR-018 depends on ADR-011 not moving.** ADR-011's own Sequencing paragraph is the citation a future reader needs (`ADR-011:94`), and its trusted-holder delta (`ADR-011:27`) stays a statement about N devices, not N machines.

### Invariants that hold, unchanged

Listed so nobody "fixes" one of them while making the phone plural:

- The whole of MM1's table: the machine believes it is paired to one phone, because it is.
- The envelope format, the AAD field set, the nonce discipline, `MailboxReceiver`'s seq/replay/age rules, PB-SYNC-1's two buckets and four repair channels, and `streamsOf` as the only bucket→channel mapping site. N pairings means N instances of that machinery, not one modified instance.
- The relay stays untrusted and ciphertext-only. Two machines behind the same organization relay are still two mailboxes with two content keys, and no confidentiality property weakens. What does change is disclosed rather than absorbed: a co-hosting relay can now correlate those two routing ids as one handset's, which is a **new** metadata fact this ADR creates and not an inherited one — see the Negative consequence below.
- Live-only input, and the no-replay rules for `uncertain` / `outcome_unknown` operations (`playbook:259-260`). Plural machines add no queue and no cross-machine retry.
- ADR-009's structured-chat surface and ADR-013's capture rulings. This ADR changes which pairing an item arrived through, never what an item is.
- "Multiple phones/tablets paired to one computer" remains an explicit non-goal of the first complete product (`playbook:1019`).

## Consequences

### Positive

- The first complete product covers the shape developers actually have — a laptop and a desktop, or a work machine and a personal one — without touching frozen crypto, the grant format, the reconcile schema, or the lease router.
- Blast radius is client-side. The daemon, the gateway, the relay protocol and the pairing handshake see one phone per machine and need no version negotiation for this feature.
- Failure isolation is structural rather than defensive: with no shared key, cursor, seq space, operation id or file, a cross-pairing bug has no medium to travel through. The R4 exit can prove isolation by construction instead of by exhaustive interleaving.
- ADR-011 stays a clean all-or-nothing slice. Nothing here creates a half-adopted M-item that a later implementer would have to unpick.
- The singleton `mobile.App` composition is retired at R4, before R5-R8 build screens against it — the migration is paid once, at its cheapest point.

### Negative

- A durable-artifact migration of the phone's state directory, with the full read-verify-namespace-commit discipline and a rollback-readable window of one release train. It is the highest-risk item in R4 and it runs on handsets in the field.
- Per-machine everything means N connection loops, N relay sockets in the foreground, N wake addresses and N cursor sets: real battery, socket and Keystore-round-trip cost, bounded only by MM3's cap. The cap is a product-visible limitation — some rows are deliberately not live — and it must be rendered honestly rather than hidden.
- The bound gomobile surface grows a manager layer and every scalar read model (`StateSummary`, `MachinePresence`, `Freshness`, `Event`) becomes machine-qualified. gomobile has no bound list type (`mobile/types.go:76-79`), so each plural read model costs another handle type.
- `(machine_id, session_id)` must be threaded through every screen, deep-link, cache key and operation record. A single site that keeps a bare session id is a cross-machine confusion bug that only shows up when two machines coincide on an id — which is exactly why R4 and §11.2 force duplicate ids into the test matrix.
- Forget-versus-revoke is now two operations with two copies and two partial-failure stories, on a screen where the user is already anxious. Getting the copy wrong is a security-relevant defect, not a polish defect.
- **A shared relay gains a co-ownership correlation it did not have.** The session relay's declared observation scope is "Routing ids, timing, sizes, presence, retention metadata" (`playbook:350`), and a single-machine phone gives one relay one routing id. Two pairings on one organization relay put two routing ids behind one handset's connection, presence and timing pattern, so that relay can infer the two machines are co-owned. R4's exit deliberately creates this arrangement — "two through the same organization relay and one through a separate relay" (`playbook:763-764`) — so it is a designed disclosure, not an incident. It stays inside the declared scope's shape (still routing ids, timing and presence; still no content, and each mailbox keeps its own content key), but it is a fact the relay learns *because* of this ADR. ADR-015 push-gateway split refuses the analogous one-address-across-N-pairings gateway design for the same correlation reason; the difference is that the relay is the developer's or their organization's own service, while the gateway is Swarm's — a self-hosted relay operator is already trusted with that machine's metadata, and a user who does not want the inference splits the pairings across relays, which the same R4 exit proves works. The deployment guide already owes the operator "Metadata visible to their relay" (`playbook:993`); this inference is now part of what that sentence has to say, rather than something a reader is left to derive.
- Multi-machine shipping first means the ADR-011 program stays unimplemented while the app visibly manages "devices" and "computers" in the same UI. The vocabulary has to hold the line the ADRs hold.

## Alternatives Considered

**One shared state namespace with machine-id-keyed records.** One blob, one keystore container, one cursor table, rows keyed by machine id. Rejected: it puts N pairings' custody behind one file, one schema version and one migration, so a single corruption, a single future-schema refusal, or a single migration bug crosses every pairing at once. The current code already demonstrates the failure mode at N=1 — a machine-id mismatch discards "the pairing, the epoch, the sealed content key, the relay cursor and the durable send-seq ceilings" wholesale (`internal/phonecore/s9_machineid_test.go:14-19`) — and the shared design would make that a fleet-wide event instead of a one-pairing event. It also makes MM7's isolation rule a property somebody has to maintain rather than one the storage layout gives for free.

**Multi-machine implemented on ADR-011's machinery.** Reuse `SenderKeyID`, per-device inbound keys, per-device seq spaces and the keyed reconcile group to distinguish machines. Rejected as a category error: those primitives distinguish **N senders inside one epoch on one machine**, and multi-machine has one sender per epoch on each of N machines. There is no shared `ContentKey` to defend against a peer, no shared inbound bucket to fork, no shared reconcile record to key, and no peer to arbitrate a lease against — every problem M1-M9 solve is absent by construction. Adopting them would import a frozen-crypto grant-format bump, a forced re-grant of every paired device, a GG-7 wire change and an unwritten admin-tier ADR (`ADR-011:110-115`, `ADR-011:59`) to buy nothing, while landing exactly the partial adoption ADR-011 forbids.

**Multiple `mobile.App` instances with no manager, one per machine, orchestrated in Kotlin.** Rejected: it moves lifecycle, the connection cap, the aggregate event stream and the migration into the layer with the least test coverage and the most process-death exposure, and it contradicts the playbook twice: "Keep foreground connection lifecycle in the Go/mobile core; marshal callbacks to Android's main thread through a bounded, observable queue" (`playbook:569-570`) and "The aggregate UI reads immutable snapshots from `MachineManager`, not mutable singleton globals" (`playbook:574`). It also gives no single owner for "never two live send sequencers for one pairing" (MM6), which is the invariant most likely to be violated by a lifecycle race.

**Defer multi-machine to after R6-R8 and ship single-machine chat first.** Rejected on cost, per R4's stated purpose: "remove singleton state before the final chat screens make it more expensive" (`playbook:753`). Every screen built against a scalar `App` is a screen migrated twice.

## Notes

On numbering: 014 stays reserved by `docs/specifications/mirror-program.md` M3.1 for paged interaction history (`ADR-013:309-312`, "`docs/specifications/mirror-program.md` M3.1 has likewise reserved **014** for paged interaction history"), and 015-018 are allocated together by wave R1 for the four playbook §3 amendments — 015 push-gateway split, 016 Web-PKI relay TLS, 017 capability-driven terminal fallback, 018 this one. They are one allocation from one line, not a twin-pair collision of the 007/008/009/010 kind.

This ADR is short on new mechanism on purpose. Almost every ruling in it is a *boundary* — what is per-pairing, what is shared (nothing), what the machine is not told, and which frozen sites stay frozen. The failure mode it exists to prevent is not a missing feature; it is an implementer reaching for ADR-011's per-device primitives because both features contain the word "multi", and arriving at a grant-format bump, a re-pair of every handset in the field, and a half-built peer-adversary model that no product decision asked for.

One factual correction against the drafting brief, recorded here rather than silently: the phone's durable schema is at `StateSchemaVersion = 12` (`internal/phonecore/state.go:144`), not v2 — v2 is a historical version in that file's changelog comment (`state.go:40-44`). The property the brief meant is true and is what MM6 relies on: whatever the version, there is exactly **one** blob per state directory and its `machine` field is a destructive load-time filter.
