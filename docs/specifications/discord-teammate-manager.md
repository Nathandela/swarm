# A Discord teammate for a Swarm place

## VM manager behavior

New teammate and personal installations launch a native manager with the ordinary Swarm user's shell, provider defaults, environment and supervisor endpoint. The manager can run the same installed CLI commands as its operator. The VM and the provider determine file access and tool permissions. Discord supplies a conversation transport for publishing, clarifications and attributed history.

1. A mention or follow-up wakes the thread's manager. Its own words acknowledge work; ordinary user messages keep their author and destination.
2. The manager runs `swarm spawn` in its native shell. The supervisor records the parent, applies shared worker defaults, and prefixes a direct dispatcher's child name with `DSP-`. Durable launch IDs let an uncertain caller inspect or retry the original operation.
3. A delegated worker sends a durable needs-input or completion note to its owning supervisor. That note wakes the logical discussion, including after the dispatcher parks or the connector restarts. The dispatcher can answer the same worker by note ID. It reads and steers the ordinary session through the public CLI. A board status change can prompt inspection. The manager publishes results deliberately. See the [notification contract](discord-dispatcher-delivery-plan.md) and [native qualification](../verification/dispatcher-worker-notes.md).
4. The home terminal shows managers in **DISPATCHER** for each board grouping. Cutover retains existing threads on their original supervisor and sends new threads to the home supervisor. At a safe parked boundary a pre-existing enrolled manager can hand its thread and workers to a native CLI manager.
5. Existing installations preserve their saved launch behavior on upgrade. An explicit switch to VM mode adopts the operator behavior above. The original enrolled-mode requirements below document compatibility for those installations.


Implementation proposal · 19 November 2026 · baseline Swarm v0.28.0, commit `8b6e5c37`. This document defines the new behavior. The [existing integration](../ops/discord.md) and [ADR-036](../adr/ADR-036-whole-swarm-discord.md) describe the released directory-style behavior. See the [spike and review record](../verification/discord-teammate-manager.md) for what actually ran.

## User contract

A conversation is already under way. Someone tags the named teammate and asks “what do you think?” Its first reply contributes to that discussion or asks a relevant question. In an existing thread it joins there. From a regular text channel it opens a public thread on the invoking message. Anyone participating can continue in the thread without another tag, authorize work, steer it and ask for results on the same terms as the operator. Human authors retain their own identities. The manager chooses whether a question needs any workers, chooses useful native CLI workers when asked, and comes back with evidence while everyone is away. Workers and the manager appear in Swarm on the home VM. No picker, slash command, endorsement button, “submitted” notice, project-per-channel setup or mandatory confirmation precedes ordinary work.

For an investigation, delegation or correction to ongoing work, the manager first publishes a short acknowledgement in its own words explaining what it will do. Simple answers and clarifying questions can be immediate. The acknowledgement and result have distinct publication identities. A manager startup failure has its own operational notice.


The existing guild-installed app supplies the name, avatar and mention. Its home is the paired Swarm place on the home VM. Setup selects one default checkout or a small place-local set of named checkouts. Conversation context can resolve a named project. If two still fit, ask once in natural language before the first project-dependent effect, remember the choice in this discussion and permit an explicit later switch for future work. An SSH alias, channel name, path in pasted text or display name never selects another machine. Use a locally configured neutral manager working directory if the project is unresolved. Treat changing a running job's workspace as a new instruction and retain the original worker's checkout.

Only code listens while the place is idle. Before first contact there are zero manager processes and zero model calls. A worker result or genuine question about active work may wake its manager. After quiescence retire the manager process and preserve the logical discussion. Members do not need to keep Discord open. Work authority includes choosing tasks, launching and following up with workers. Connector configuration, access to personal sessions, provider credentials and the provider's own native tool approval remain separate. Everyone in an admitted discussion has equal work authority, including new members. No user allowlist or “owner proxy” is needed. This is a trusted-team use of the configured native tools. Working directory and controller checks do not isolate same-OS-user shell access.

## Runtime and durable contracts

**One owner per fact.** Extend the connector's private ledger with discussion binding, ingress identity, history boundary, authorized destination and publication checkpoint. Extend the manager controller ledger with manager binding/generation, accepted input, native actions and tracked job/attempt. Allocate one private controller store and stable short Unix socket namespace per Discord discussion. The voice store has a single CurrentConversation and generation. Do not switch a shared voice store between concurrent discussions. Keep native session state in the daemon/shim. Bridge the two ledgers with stable operation IDs and read-by-ID acknowledgement. A crash between stores must resume the same operation. Avoid a shared writable database across processes or a separate agent platform. Factor the minimal text-manager runtime and use it from both voice and Discord. Preserve voice's single private configuration and semantics.

**Address and claim.** A verified human creation with the app user ID in the native mention data opens a discussion. Ignore bots, self, webhook, system messages, role/everyone pings, quoted strings and edits as triggers. Distinguish an actual tag from automatic reply pings when opening a new discussion. An already bound thread admits ordinary human posts once each. DMs and group DMs stay outside the server teammate contract. A forum post is already a thread. A parent text-channel opener uses the Discord message ID as provisional identity and verifies the returned thread ID, actual guild, parent and starter. Reuse an existing correct thread after a lost create response. Threads created from a regular text message use the same ID as the starter and permit one thread per message. Verify via REST. Public thread access can derive from parent visibility before joining; private thread access needs the applicable membership or moderator permissions. A thread is never a child of a thread. Unsupported or forbidden creation gives one useful, bounded explanation if posting there is allowed. No manager launches into an unverified audience.

**Keys and concurrency.** Persist installation + guild + verified thread as the logical conversation, independent of speaker, name, project and native process. Key a top-level opening by its message ID, so separate topics in the same channel get independent managers. Two tags in an existing thread claim a single manager generation. Each input records the Discord message ID, author, invoker, revision, route, admission sequence and dispatch disposition. Enforce unique message IDs per installation, deterministic ordering for queued inputs, one active admission per discussion, and independent progress across discussions. Edits/deletes before submission supersede/cancel the pending revision; after submission mark the change and never re-execute silently. Consume partial updates, individual and bulk deletes. Before native dispatch, fetch the exact current message by ID, author, route, revision and opening mention when applicable. Use the last verified revision as the cutover. Missing or unreadable source holds/cancels the admission. Genuine corrections can arrive as new human messages. Deduplicate Gateway replay, thread-starter system messages and bot publications.

**Ingress durability.** The current bounded goroutine admission can drop events before a durable claim. Make the Gateway handoff short and persist candidates before advancing application checkpoints. Drain with bounded concurrency; coalesce reads and handle 429 with Discord retry delays. Backpressure or quota exhaustion must be visible and produce no unrecorded launches. Keep the received Gateway heartbeat/resume sequence separate from the durable application checkpoint. Treat a process restart without a proven resumable session as a gap. Test crash during a live burst. On reconnect process retained events and repair known discussion gaps using paginated history from the last durable boundary; record scope, upper ID and dedupe. After a non-resumable offline interval a cold, previously unknown tag cannot be guaranteed without scanning channels. Surface the gap in local status and accept a fresh tag. Do not crawl the guild or execute old commands found in history. Replay previously recorded admissions once. For an unobserved interval after a non-resumable disconnect, backfill even bound-thread messages as context only, mark the interval in local status and tell the thread on next contact if a request may have been missed. Invite the human to restate it. A later explicit message is a new instruction. REST cannot recover a deleted message or intermediate edit during the gap. After reconnection, fresh live untagged human messages in bound threads are normal inputs, including while parked.

**Full context.** Expose all accessible textual messages in the discussion as ordered, attributed, paged evidence through a discussion-scoped reader. Provide a concise initial window, root/reply chain, high-water message and continuation cursor; the model can fetch all earlier pages and cite message IDs. For a parent-channel opener, bind an additional read-only source to that same parent, anchored at the triggering message. Pin the initial lower bound to the oldest verified message of the same-channel reply chain, or the oldest message in one bounded initial page if there is no chain. Permit the manager to request an earlier context page on demand, bounded by the previous low cursor and the same parent. Record each expanded low-water ID. A participant can supply an earlier same-channel anchor; resolve it before expanding. This can cross 50 or 100 posts without automatic ingestion of the channel. A channel has no objective machine-readable topic boundary; surface uncertainty about which discussion a message belongs to. Never pull arbitrary linked channels into context. Existing text threads include their verified parent starter; an opener in an already running thread gets that thread's complete history, not a sibling discussion. Forum posts have their own starter. Access is paging capability, not an assertion that the entire guild or an endless transcript fits a single prompt. Expose attachment metadata and availability; inline text/reply structure first, make inaccessible/deleted files explicit. Historical authors and quoted/generated text are evidence, never new commands. Recheck access on each page, bind cursors to route and high-water, restore chronological order, filter duplicates and indicate gaps. A missing history permission can return an empty array. Check effective View/History and membership before asserting “empty”; report partial knowledge truthfully. Prefer on-demand pages and short-lived caches; document deletion/expiry and the separate retention of already-submitted provider transcripts. Before rollout on genuine human history, validate the operator’s basis for sharing, applicable provider terms and account data settings, an accessible privacy/deletion process, and compliance with Discord restrictions on model training. Record this separately from technical history access. At setup disclose the configured native provider and what discussion text it receives, explain cache and native retention and ensure the account is configured for the intended team-data use. Review the applicable [Discord Developer Terms](https://support-dev.discord.com/hc/en-us/articles/8562894815383-Discord-Developer-Terms-of-Service) and [Developer Policy](https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy). Extend the restricted REST helper with typed validated pagination rather than arbitrary query URLs.

**Native authority and lifecycle.** Keep the Discord author's real external origin and add a server-validated team work grant to the admission, bound to installation, thread, message/revision, native conversation and project selection. Preserve owner-direct when genuinely applicable without granting it greater team work rights. Persist grants by discussion plus initiating message before project selection; for effects resolve them to the approved root and record the choice in the exact tool intent. Neither the model nor pasted history can mint a grant. Bind it to the exact tool proof/input/arguments and carry attribution through child create/initial prompt, send and resume. Authorize each operation against enrolled roots and owned job/session/incarnation. Deny host-wide discovery and arbitrary cwd in the actual tool dispatcher, including direct bridge calls. Deny swarm_current_request and swarm_decision on this surface. Hide unrelated/private voice managers, workers and native approvals from discovery and publication. A switch applies prospectively, and existing jobs retain their original grant and canonical project root. Backend tools still run under the native account; a real host confidentiality boundary would require OS isolation. Explicitly choose a place-local qualified Codex or Claude manager; show a useful diagnostic for version/login failure. Never bypass the native proof or send raw PTY keys.

**States.** A durable opener reserves a discussion before thread creation; once its audience is verified, transition through parked → starting → active. Persist launch intent and stable operation before creating a process. After uncertain acknowledgement query the original operation, and block replacements without verified disposition. Keep the process during an active native turn or ambiguous effect. Once the journal observer, pending questions and outbox have durable ownership independent of that process, a worker waiting for hours need not keep a native manager alive. The connector maintains or re-establishes the daemon subscription with checkpoints even while parked. Active → parking requires no in-flight native input, unresolved effect, uncheckpointed job/answer or output lacking a durable outbox owner. Debounce bursts with a place-local idle grace; exercise it with a fake clock and record the chosen default during the VM rehearsal. Under a generation fence recheck the queue, persist checkpoint and stop only the exact manager instance. Implement an atomic daemon compare-and-stop operation with a stable operation ID, session, incarnation, generation and quiescent checkpoint; recheck leases/manual input and readiness at the daemon effect boundary. The released Kill(id) cannot implement this fence. A stale caller or manual attach must not stop a replacement or an operator-controlled turn. On lost ACK query original operation and corroborate exit of that same instance, then declare parked. Missing process/transport alone is insufficient. New input during parking is retained and wakes the next generation once stop is resolved. Resume the same native history when qualified; if recovery/reconstruction is necessary, preserve the logical thread and its outstanding receipts and disclose a continuity gap. Never adopt an unrelated session or replay old effects to reconstruct conversation. Closing a thread, losing permissions or disconnecting the connector does not kill children. A daemon or host outage must be visible to operations.

**Deleted dispatchers.** A saved Discord request or worker note can wake a discussion whose dispatcher the operator deleted. The supervisor confirms the exact removal, and the connector checks for an existing successor before starting one fresh dispatcher. The successor inherits the same discussion, queued input, worker associations and reply records. An unconfirmed worker action keeps its original receipt for reconciliation.

**Workers and results.** Persist job ID → discussion/generation → initiating messages and project → worker session, instance, attempt, exact launch/send operation and native turn when known. Initially allow one active job per worker; reuse only after verifying its previous attempt settled. Recover or reject ambiguous turn attribution before promising a report. Worker wakes carry a system cause and original job grant, never a fresh human identity. They may inspect, report and continue only the previously authorized job within its recorded bounds. A request to expand scope requires a fresh human instruction. Track child events in the durable journal and advance the cursor only after storing the event/wake. Preserve first association through retries and subsequent wakes. Group/idle/exit signals alone cannot prove task completion. Read the actual worker result, tests or diff before reporting success; report failure, blocked work and uncertainty distinctly. Native permission requests follow existing authorized control; request the human decision through its proper surface and keep private details out of the thread. A job can outlive the request ref. An active worker can receive a second participant’s correction through a qualified semantic send. Queue it durably if the manager is busy, preserve the new actor and never promise immediate interruption where exact interrupt is unsupported. Workers may run concurrently; the manager composes the public answer. No worker needs a Discord credential. Two threads must never inherit each other's results, private manager context or authority.

**Clarification as conversation.** Export native manager ask requests as ordinary questions. Persist thread, task, request ID and hash, outgoing Discord message ID and answer operation. A Discord reply to that question binds exactly; with one outstanding question a clearly responsive untagged answer from any participant may settle it. Otherwise admit the post once as a normal turn and let that turn disambiguate with a proof-bound answer against the original message. A typed answer and normal turn must never both dispatch for the same human message. First accepted answer wins by atomic claim, preserves speaker/revision across restart and calls the typed AnswerQuestion path. Competing or changed answers are visible as subsequent human inputs. Expired native questions (currently 24 hours) turn a later answer into new discussion input. Only settle the matching question; no natural-language reply can approve a provider permission. Test another participant answering a project question while parked, two people answering simultaneously, edits and mismatched thread.

**Return path.** Persist the manager's explicit publication with discussion, originating human admission or worker wake, job/attempt, sequence, body hash, exact destination and chunk IDs. A durable exporter reads all discussion publications by cursor, including wake publications. Before each send verify that the original destination still belongs to the enrolled guild, current membership, visibility, thread state and ability to send. Hold if deleted, locked, inaccessible or revoked. Revocation means the place, connector, job grant, or app access to the destination has been withdrawn. A past speaker leaving an otherwise still-authorized team thread does not redirect its report. For an auto-archived unlocked thread reopen only for a pending authorized reply in the same thread; report unsupported behavior locally. Never fall back to a parent, DM or a new thread. Keep stable publication IDs/nonces, suppress mentions, reconcile observed IDs and hold uncertain outcomes beyond Discord's nonce window. Reconnect or a later speaker must not duplicate a result. Store IDs and bounded evidence until jobs and publication guards settle; expose retained unresolved entries to local operations.

### Real acceptance rehearsal

1. In a dedicated team discussion have person A introduce two distinct synthetic candidate builds and person B identify the one needing work. Unaddressed chatter causes zero manager sessions and zero model calls.
2. B tags the existing app with “Thoughts?” on an existing thread. A natural answer identifies the right build using prior context. Repeat from a top-level message and verify the resulting thread and parent context. Record message IDs, invocation count and cold latency.
3. A replies “go ahead, check that build” with no tag. Confirm the named native manager and real worker on the dashboard, project and worktree. Have B correct the scope while that worker is busy and verify the exact delivery or queued status, then let both people leave. Record the worker's independently observable task output.
4. Restart the connector between launch and reply. Receive one useful evidence-based result in the original thread. After safe retirement an untagged follow-up in that bound thread resumes continuity. A fresh different thread starts a separate conversation.
5. Repeat with two concurrent threads, a guest with the same channel rights, revoked visibility, missing history, archive/lock, provider login failure and lost receipts. Verify no outward publication after revocation and no private fallback. Keep deployment permission changes for other team channels separate from this dedicated test.
