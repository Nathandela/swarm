# Codex remote resume version boundary

## Incident and change

Swarm 0.14.0 on Codex 0.157.0 retained the saved conversation IDs and rollout
files for five WIP discussions, but every resume exited with `Permission
overrides are not supported when resuming a remote task.` The adapter prepared
corrected arguments; `backendResumeCommandArgs` discarded them unless the live
backend reported exactly 0.154.0 or 0.156.1. The shim then appended `--remote`
to the original arguments, restoring the rejected permission overrides.

The gate now selects the existing corrected arguments for numeric stable Codex
versions >=0.154.0. The existing banner parser and SemVer validation reject
unknown, malformed, short, prerelease, and build-suffixed tokens. Fresh launches,
standalone fallback, backend sandbox defaults, and saved-profile precedence are
unchanged. No new dependency or protocol/schema version is introduced.

## Upstream contract

Exact tagged OpenAI Codex source establishes the boundary:

- [0.153.0 startup](https://github.com/openai/codex/blob/rust-v0.153.0/codex-rs/tui/src/app/startup.rs#L330-L345) predates the remote-resume permission guard.
- [0.154.0 startup](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/tui/src/app/startup.rs#L428-L443) rejects permission overrides on remote resume.
- [0.157.0 startup](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/tui/src/app/startup.rs#L463-L478) retains that guard.
- [0.157.0 resume parameters](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/tui/src/app_server_session.rs#L2116-L2123) omits client permission overrides for remote resume.

This is a version-boundary contract, not a claim that every future Codex release
has been tested. Provider upgrades should exercise native resume and restored
permissions; adding individual versions to an allowlist recreates this incident.

## TDD and review

The expanded regression failed before implementation at 0.154.1, where the old
gate returned no alternate arguments. It passed after replacing the exact-version
gate. Coverage includes 0.154.0, later patch/minor releases, 0.157.0, 0.200.0,
1.0.0, pre-boundary versions, malformed numeric tokens, and suffix rejection.

A Sol agent implemented the test-first change; a separate Sol agent checked the
upstream contract and native runtime; Luna independently reviewed the shared
call path, parsing, fallback, and policy preservation. Review added malformed
leading-zero and junk-suffix cases. The parent reviewed the final diff.

## Native Codex 0.157.0 probe

An isolated Codex home and a genuine completed no-tool thread exercised the
actual remote TUI. Either `--sandbox workspace-write` or
`-c sandbox_workspace_write.network_access=true` reproduced exit 1 with the
permission-override error. Removing both opened the saved thread, and its
`thread_settings_applied` record retained filesystem write entries and network
`enabled`. A subsequent native `thread/resume`, with workspace-write/network
server defaults, returned `on-request` approval and `workspaceWrite` with
`networkAccess: true`.

This isolated probe used loopback WebSocket: the temporary Unix listener failed
Codex's host socket-directory validation. The same remote TUI startup path is
exercised, but deployed Swarm Unix-socket acceptance is a separate rollout check.

The resumed thread then completed an authenticated no-tool turn. The probe's
buffered stdout reader missed the completion notification, but the isolated
rollout records `task_started` at 14:05:49.651Z and `task_complete` at
14:05:54.465Z on 2026-09-25, following the applied network-enabled policy. This
is provider-history evidence, not an inference from an open TUI.

A saved `:read-only` profile stayed read-only with network disabled when resumed
against conflicting workspace-write/network-enabled server defaults. A copied
legacy thread without a profile instead adopted read-only when given that server
default, confirming why Swarm must keep carrying its recorded sandbox setting.
