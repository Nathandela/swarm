KNOWN GAP -- REAL, AND DELIBERATELY NOT FENCED HERE

Rule 3 refuses a daemon.env that is absent or empty. It does NOT refuse one that
is non-empty but DEGRADED, and degraded is the likelier failure. Raised by lane A
after this suite was green.

The mechanism: daemon.env is rewritten on every daemon start from that daemon's
own environment (the plan's L2, "an interactive start refreshes it"). A daemon
started from a poorer environment therefore overwrites a good file with a poorer
one. FilterEnv over a launchd or cron context keeps PATH=/usr/bin:/bin:/usr/sbin:
/sbin, HOME and SHELL, and carries no provider key. Three lines, non-empty, so
len(env) == 0 does not fire; rule 4 spawns from it; the phone-launched sessions
that follow cannot resolve `claude` on that PATH and lose ADR-006 billing
inheritance. It is self-stabilising -- every later unattended restart faithfully
rewrites the same degraded content and logs "converged" each time.

Narrow today: EnsureDaemon (cmd/swarm/main.go:266) and the two daemon.Restart
call sites are the only ways a daemon starts, and under the plan as designed the
timer never spawns from launchd's environment (rule 0 exits first; rules 1-3
cannot spawn; rule 4 uses the saved slice). The exposure is any OTHER `swarm`
client command run from a launchd or cron context, which D-1 auto-starts a daemon
for. Section 6 names environment STALENESS (rotated keys) but not degradation.

A read-side guard was considered and rejected, not merely skipped. The proposed
form -- warn when the saved env carries neither ANTHROPIC_API_KEY nor
OPENAI_API_KEY -- misfires on healthy machines: internal/persist/env.go's
allowlist carries no Bedrock, Vertex or subscription-auth variable of any kind,
so a subscription-authenticated Claude Code user, a Bedrock user and a Vertex
user all have a saved env with no provider key and nothing wrong with it. The
warning would fire every night, forever, on those machines, and a nightly line
that is wrong on a healthy machine trains its reader to skip the night it is
right. It is also false-negative-prone: a cron context that DOES export the key
but carries launchd's PATH passes the check and is still degraded.

The invariant belongs where the file is written, not where it is read. A
predicate on the read side is a proxy for a write-side rule, and lane A declined
to change the write side because both candidate fixes contradict the plan's
"rewritten on every start" -- a decision change above a lane's footprint. The
same reasoning disqualifies a proxy for it here.

WHAT THE WRITE-SIDE RULE IS NOT. An earlier draft of this section said the
write-side rule would be "exact" where a read-side one guesses. That was too
strong. The form proposed for it -- refuse to overwrite when the incoming set is
a strict subset of the stored one -- has two defects, both found by lane A after
this section was first committed:

  1. It must compare KEY SETS, not KEY=VALUE entries. In the poisoning case PATH
     is present on BOTH sides with different values (a homebrew prefix against
     /usr/bin:/bin:/usr/sbin:/sbin), so an entry-wise subset test never fires: it
     fails to detect precisely the case it was written for. The distinction is
     invisible until someone implements it.
  2. Even in its key-set form it silently breaks the documented repair path. An
     interactive restart that legitimately drops a variable -- a deactivated
     conda env, an OPENAI_API_KEY the owner stopped exporting -- is also a strict
     subset by keys, so the guard refuses the owner's own refresh, and after a
     permanent unset the file can never update again. The plan's answer to a
     stale saved env is `swarm daemon restart` from a terminal; a guard that can
     make that command silently do nothing is a worse failure than the one it
     prevents, because the owner has been told it works.

It therefore trades a rare silent degradation for a rare silent
refusal-to-repair, which is not a clear win. The deeper reason both proposals
fail: content cannot recover provenance. Comparing two environments cannot tell
you WHO started the daemon, and that is the only thing separating the owner's
terminal from a launchd context. Provenance is known at the spawn site --
cmd/swarm knows how it was invoked, and could mark the spawn so that only an
interactive start refreshes the file. That form is exact where both read-side and
content-comparison guards guess, and it is squarely ADR-020's to decide, in a
lane neither this one nor lane A owns.

Recorded for the orchestrator as a section 6 risk and, if the decision goes that
way, an ADR-020 amendment. Not implemented in this lane.
