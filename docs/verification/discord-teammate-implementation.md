## Scope of the release decision

Keep the feature branch untagged until integrated source passes the repository's normal and race gates, the final independent review closes its findings, and the dedicated-channel home-VM rehearsal proves human mention, ordinary cross-author steering, delayed result, retirement and continuation. Synthetic authors, a bot echo, and an app-server launch receipt are different observations. Record the final disposition here when those checks have run.

## Candidate integration and review

Two independent Astra reviews covered native custody/lifecycle and Discord admission/publication. Follow-up reviews checked the incoming and outgoing grant boundaries, revision ordering, scope revocation, passive worker recovery, question provenance, bounded history pages, and parked readiness notices. The reviewers approved the resulting source in those areas. Review approval and real-user acceptance are recorded separately.

The opt-in [native lifecycle rehearsal](../../internal/teammatemanager/hosted_test.go) uses a real installed Codex account with a private daemon and a disposable worker checkout. Supply an absolute production-binary path and an already trusted manager directory. It does not connect to Discord. Each run uses two synthetic speakers and a random file value outside the manager prompt.

```sh
SWARM_TEAMMATE_TEST_BINARY=/absolute/path/to/swarm \
SWARM_TEAMMATE_TEST_MANAGER_DIR=/absolute/trusted/workspace \
go test ./internal/teammatemanager -run '^TestHostedTeammateLifecycle$' -count=1 -timeout 15m -v
```

On the Linux VM, one rehearsal observed a prior-context answer in 9 seconds after admission, a worker launch in 13 seconds, and a job/attempt-bound verified file result 35 seconds after closing and reopening the controller. The native process retired after 2 minutes 2 seconds of quiescence and returned the same conversation's answer on an untagged continuation in 11 seconds. The complete run passed in 200.56 seconds. The later steering variant additionally requires another participant to obtain a second random value from the same worker. An initial run of that variant failed: the client queued the follow-up, the daemon rejected its conversation binding, and the worker received no second turn. The correction binds the queued action to the native manager conversation separately from the chat discussion ID and checks lease, incarnation and native idle before sending. On the subsequent 256.25-second Linux run, both random file values were verified across restart. One worker handled two distinct native turns. Its follow-up client input ID matched the durable admission receipt. The run also passed idle retirement (2 minutes 13 seconds) and untagged continuation (5 seconds). A final run with turn-pinned historical reads passed in 212.75 seconds (cold context 9 s, worker launch 12 s, verified result after restart 44 s, both same-worker results available, retirement 2 min 12 s, continuation 6 s). The isolated roster and an independent process inventory confirmed cleanup. These actors were synthetic; the model, VM worker, files, supervisor, and receipts were real.

A separate Linux app-server probe issued the same metadata-only resume against the same authenticated synthetic worker three times. Two attempts returned `-32601 list_turns is not supported yet`; eight seconds after the first attempt, the server returned the requested thread identity. Swarm retries only this exact code/message combination within its existing join deadline. Transport faults, other missing methods and wrong thread IDs retain their existing handling.

The dedicated live server connector passed read-only identity, Gateway, effective channel permission, daemon capability, native CLI and login checks. Immediately after the connector reached READY, the isolated supervisor roster contained zero sessions. A synthetic bot message in the channel did not create an agent. No ordinary server permissions or installed release binaries were changed for this rehearsal.

## Scoped worker messages in v0.29.1

Set `SWARM_TEAMMATE_TEST_WORKER_MESSAGE=1` with the rehearsal command above to run the bidirectional message check. On macOS with Codex 0.170.0 and an isolated supervisor, one native worker ran the candidate `swarm teammate message` command from its own shell. The native manager published an unpredictable marker available only in the worker's fixture file, with the exact job and attempt attached. The same worker received a native `swarm_send` reply and wrote the expected manager-only value to a second file. The final negotiated-bridge candidate passed in 99 seconds. The manager received and published the worker's marker in 62 seconds, and the worker wrote the reply five seconds later. The roster contained one manager and one worker. This rehearsal used synthetic Discord admissions and a local publication sink.

Protocol tests verify the owner-only negotiation, the delegation requirement, and binding of the worker bridge in the exact owner launch hash. Controller tests exercise the private Unix bridge and reject mismatched session or token, use of the manager credential, and a changed payload under the same message ID.

The Claude worker uses a stored response retrieved by message ID. Its local integration test covers delivery over the authenticated Unix bridge, one response per worker message, original Discord source revalidation, and rejection after worker retirement. The opt-in rehearsal accepts `SWARM_TEAMMATE_TEST_WORKER_MESSAGE=claude`. On the Mac, Claude Code 2.1.326 launched with its worker instructions and displayed an expired login before it could run the command. A real Claude model turn remains unverified.

For the v0.29.1 personal-DM and standing-instruction spike, add `SWARM_TEAMMATE_TEST_PERSONAL=1` to the native lifecycle command above. A Mac run opened one native Codex manager from a synthetic owner DM and read a random check word from the place settings. The test then changed the instructions and asked the same question in the same DM. The two distinct expected answers arrived in 10 and 7 seconds. The full run passed in 24.88 seconds. This check used the real Mac manager and a synthetic Discord transport.
