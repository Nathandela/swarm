# Discussion creation and manual account changes during rotation

Tested November 18 on feature base `a94d40f0` and main `2d9dc63d`. The Linux VM daemon ran Swarm 0.26.0. Its shell also had an older 0.11.2 executable under ~/go/bin. The doctor confirmed the daemon matched /usr/local/bin/swarm. No daemon, existing discussion, installed binary or selected account was changed for these experiments.

## Installed native clients

**Claude.** Against a loopback Messages fixture, create a conversation with `--session-id` in configuration A. With the same working directory, `--resume` in B exits 1 before sending any Messages request. Creating a new B conversation succeeds. Resuming the original conversation in A succeeds. Keeping that original configuration and changing only the synthetic API key at successive process launches also succeeds with A, B and A. The fixture saw message-array lengths 2, 5, 8 and 11 on successive requests for the original conversation. Both platforms gave the same result. These were explicit submissions with fake API keys, separate CLI processes and ordinary disk history. They establish the importance of history location. They do not establish hot OAuth adoption or automatic continuation. Anthropic documents configuration directories as owning history and login together. [Authentication](https://code.claude.com/docs/en/authentication)

**Claude concurrency and retries.** On both OSes, start a request in a fresh native discussion. Hold its response at the loopback server. Create a second discussion in the *same configuration and working directory* using an independent synthetic API key; it completes before the first response is released. Return a transient 529 overload to the original process. It retries once and completes under its original synthetic key without host resubmission. The request sequence was A, B, A. A fleet-wide idle barrier would have delayed a healthy birth here. A host that also retries can duplicate work.

**Codex.** On each OS, initialize two native app servers concurrently. In each, verify an empty account, start three ephemeral read-only threads, list the loaded IDs and read each thread by ID. All six fresh IDs were unique. Neither server listed the other's threads. An unsubscribe returned success while the ID was still loaded throughout a roughly three-second observation. Inventory is therefore insufficient to infer listener custody. The Linux experimental schema has no loaded-only option on thread/resume. Its thread/attachment/add creates a stored attachment with a payload. It does not attach a lifecycle observer.

On Linux, repeat with two isolated backends and install synthetic external-auth selections A, B and A independently in each through account/login/start. The native method acknowledged all six installations. With workspace routing deliberately unavailable, account/read failed after each installation. All six subsequent thread creations still succeeded, and previously created thread IDs remained readable across the switches. The first account/read also failed on macOS in this failure-injection case. A native acknowledgement, successful thread creation and usable account routing are three separate facts. These fixture threads performed no inference.

**Real service control.** On the VM, the native login status for each default profile indicated signed in. In an empty disposable project, Claude (Haiku, safe mode, empty tool set, no session persistence) and Codex (ephemeral, read-only, ignore user config) each answered a single fixed prompt with the expected marker. A separate native Codex account/rateLimits/read succeeded. The exact query used by Swarm also succeeded with excludeResetCreditDetails=true. The account ID was present, ordinaryUsageAllowed was boolean, the default bucket ID was codex, and the only reported duration was 10,080 minutes. The bucket included spendControlReached. No credential, identity, private prompt or quota response was retained. The default Swarm registry contained zero saved logins, no selected provider account and no pending switch. This qualifies one working native login per provider on that host. It gives no live second-account A→B→A or quota-recovery result.

## Swarm exercises

| Question | Observation |
|---|---|
| Can a pending switch block new work today? | Reproduced on main for both providers. A precommit switch rejected a different manual target. A committed switch could queue one different target. New birth was rejected while the legacy journal existed. The feature's legacy Codex mode retains that limitation. |
| Can new Codex discussions open around a manual change? | A synthetic feature-branch experiment retargeted the external-auth path 24 times. Previously prepared and newly bound launches remained valid. Sending on a published discussion waited for account readiness. No restart was issued. |
| Can a prepared Claude launch use the wrong selection after A→B→A? | Twelve synthetic profile selection cycles rejected obsolete birth authorizations even after returning to the same account. Current B births succeeded. A valid, fresh receipt, current epoch, profile and working directory were supplied. Missing readiness and between-step selection changes still need a caller that keeps the user's creation request alive. |
| Can Swarm distinguish spend controls from rolling quota? | A synthetic scoped ordinary-usage denial with spend control active and 100% weekly capacity remaining incorrectly moved native Codex to B. A second probe reproduced the same switch with no denial reason at all. The branch fix covers explicit spend/credit denial in steady selection and legacy retry. Native-grant automatic selection now requires a matching account, the explicit codex bucket, ordinary usage denied, a typed rolling-limit reason, a raw fully used weekly window and a valid future reset. Authorization expires at the earlier of the reset and 60 seconds after the observation. A rounded display of 0% remaining, a five-hour window or a missing duration cannot authorize the switch. An unexplained denial still stops submission. Manual retargeting remains available. The installed 0.169.0 schema distinguishes rate_limit_reached from four separate owner/member credit or usage denials. |
| Can it prove exactly what to restart? | Fresh targeted suites passed 21 Codex execution tests and 22 Claude control tests, including cancellation, pending tools, approvals, active retry and incomplete evidence. The default Codex spectator still lacks creator-stream custody. An early Claude question fixture never constructed a successor. The later [durable pending-question experiment](claude-structured-pending-question-2026-10-25.json) did: on both platforms Claude 2.1.310 attempted a model request while the question was unanswered. Automated submission remains unqualified. |
| Can it survive restart or a full disk? | Targeted race tests passed for login storage and migration, including failure before/after rename, reopening after uncertain writes, retirement and credential ownership. Five Claude maintenance caller tests passed. These exercise components. They do not establish an end-to-end Claude publisher, a Codex parked scheduler, or a full fleet migration. |

## Integration decisions

1. Split new-discussion creation from account adoption and inference. Retain the requested discussion and its settings across a rotation. Admit its first input only after the current selection is usable. On selection conflict, re-resolve the latest manual choice with the same creation request. An unsupported runtime needs a visible route to native sign-in. Silent fallback to another identity would run work under the wrong account.
2. Preserve the original Claude history and working directory. Pointing an old discussion at the newly selected profile breaks resume. Native same-process OAuth adoption still requires a supported operation and real account, policy and tool observations. Codex can install a different external selection while threads exist. Qualify workspace routing and actual requests separately.
3. Keep manual changes available. For automatic selection use fresh account-scoped readings, distinguish rolling quota from policy denials, and durably remember attempts so a restart cannot create a selection loop. The planned 5% source, above-10% target and 60-second freshness/cooldown policy is still a design target.
4. Recover only a positively identified quota-interrupted task, after adoption. A human question, permission wait, native retry, new user input or unknown actor state must suppress automatic submission. Preserve completed tool effects.
5. Qualify the normal Swarm create/submit path with multiple discussions, a manual retarget between prepare and submit, active native tools, both accounts, daemon restart and a disk fault. Re-run on the installed client versions. The feature's Claude custody pin is 2.1.310 and its Codex grant-refresh pins are 0.163.0/0.164.0. Broadening a version check is insufficient evidence.

The frozen Linux test binary ran 12 top-level tests on tf_nathan, with zero skips. These included all five Claude maintenance caller tests, explicit and unclassified Codex denial, ten scoped rolling-limit cases, manual precedence, out-of-order readings and relogin during publication. It used an isolated temporary home and was removed afterward. Binary SHA-256 was 6799e52b76f34349dfe582e8570c85b257412d8b38cf249e14ea615c03545af4.

The full login-store suite passed on Go 1.26.10 and the migration suite passed. The macOS custody fixture originally failed with a symlinked temporary directory. Resolving the fixture path fixed the test without relaxing production path validation.

The deciding release experiment remains two independently enrolled accounts for each provider, same discussion A→B→A, alongside a new birth, an active sibling and a sibling waiting for a human. Require unchanged history, no lost manual input, a single continued task and no repeated tool action. The branch and the live VM were not migrated or released by this spike.
