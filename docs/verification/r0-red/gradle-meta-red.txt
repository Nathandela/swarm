--------------------------------------------------------------------------------
METHODOLOGY NOTE: why --refresh-dependencies was needed on this machine
--------------------------------------------------------------------------------

The literal CI command, ./gradlew --no-daemon lint test, was run first, with no
flags added, exactly as the "Gradle gate (PB-TOOL-6)" step in
.github/workflows/ci.yml invokes it. On THIS machine it did not fail: it ran
straight through project configuration and deep into task execution
(:app:testReleaseUnitTest, several minutes of real Robolectric test runs)
without ever reaching the verification gate.

Cause: this machine's ~/.gradle/caches/modules-2 already holds resolved,
previously-verified metadata for all three artifacts (confirmed by direct
inspection -- guava-parent-33.3.1-jre.pom, junit-bom-5.10.2.module and
kotlinx-coroutines-bom-1.8.0.pom are all present under
~/.gradle/caches/modules-2/files-2.1/.../, left over from earlier local work).
Gradle treats already-resolved metadata for a fixed version as immutable and
does not re-touch or re-verify the backing files on every build -- only a CI
runner's cold GRADLE_USER_HOME (nothing in modules-2 yet) is forced to fetch
and verify them fresh, which is exactly where PB-TOOL-6 is failing in CI.

--refresh-dependencies forces Gradle to bypass that resolved-metadata cache
and re-verify from scratch, i.e. it forces this machine down the same code
path a genuinely cold CI runner takes unconditionally. The failure it
surfaces is against the same checked-in gradle/verification-metadata.xml, for
the same three artifacts CI reports, with no other flags, versions or
repositories changed -- it is the same defect, not a different one. It was
also independently reproduced faster via `./gradlew --no-daemon
--refresh-dependencies buildEnvironment` (identical "configuration 'classpath'"
failure, BUILD FAILED in 49s), confirming the failure is at root-project
buildscript classpath resolution, before any :app task runs -- consistent
with lint+test getting well past it on a warm cache.

--------------------------------------------------------------------------------
DIAGNOSIS
--------------------------------------------------------------------------------

android/gradle/verification-metadata.xml is missing checksum entries for
exactly three parent/BOM POM-metadata artifacts pulled into the root
project's buildscript "classpath" configuration: guava-parent:33.3.1-jre's
POM, junit-bom:5.10.2's Gradle Module Metadata (.module), and
kotlinx-coroutines-bom:1.8.0's POM. These are inherited/imported metadata
files (Maven parent POM and BOM import), not directly-declared dependencies,
which is why they are easy to omit when the metadata file was last
regenerated (2026-08-02) with a tool invocation that did not force resolution
of every transitive parent/BOM link. Gradle's strict verification mode
refuses to trust any artifact -- binary or metadata -- with no entry in the
file, regardless of whether the bytes are otherwise legitimate, so a cold
GRADLE_USER_HOME (every CI runner) fails at project-configuration time before
a single :app task executes. The fix is to add the three missing checksum
entries to verification-metadata.xml; this evidence file intentionally leaves
that file untouched.
