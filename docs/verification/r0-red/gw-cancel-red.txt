--- DIAGNOSIS ---

WHICH WAIT OUTLIVES CANCEL: Gateway.ForwardCommand's per-command daemon round-trip
(internal/remotegw/gateway.go:327-363, the blocking reply read at gateway.go:363
`return dc.readControl(10 * time.Second)`), reached through
CommandBridge.forward -> routeCommand -> handle -> processBatch, all invoked
SYNCHRONOUSLY and un-selected inside CommandBridge.Run's loop body
(command_loop.go:406, inside the `for` loop between MailboxWait iterations).

ForwardCommand's signature is `ForwardCommand(op string, rc protocol.RemoteCommand)
(protocol.Control, error)` -- it takes NO context.Context. It dials a fresh daemon
connection (gateway.go:328), writes the command (gateway.go:358), and blocks in
dc.readControl using a bare 10-second time.Duration deadline (gateway.go:363) that is
set on the net.Conn directly and has no relationship whatsoever to Service.Run's ctx.
When Service.Run cancels its ctx (service.go:326-327) while CommandBridge.Run is mid-way
through this call -- i.e. a mutating command (here: the test's OpLaunch) is in flight to
the daemon at the moment of cancel -- nothing in the CommandBridge.Run loop notices the
cancellation until this blocking read itself returns, either because the daemon finally
replies or because the hardcoded 10s local deadline fires. The loop's own ctx checks
(the `if err := ctx.Err(); err != nil` at command_loop.go:361/374/394, and MailboxWait's
ctx-aware select) never run again until this synchronous forward() call unwinds, so
Service.Run's `wg.Wait()` (service.go:358) is blocked for however long the in-flight
daemon round-trip takes -- observed at ~2.6s in the two instrumented captures below,
comfortably inside the hardcoded 10s ceiling but past both the 2s harness bound and, on
a slower/more contended daemon, plausibly past the 5s bound the two later test copies
widened to without diagnosis.

DIAGNOSIS RULED OUT (all checked, all correctly ctx-bound, none reproduces the bug):
  - Service.runJournal's reconnect timer (service.go:396): selects on ctx.Done(), and
    the read loop it wraps (gateway.go:206, dc.readControl(time.Second)) rechecks
    ctx.Err() at least once per second -- bounded, fine.
  - CommandBridge.Run's MailboxWait + commandRetryDelay (command_loop.go:369-398): the
    wait's own context is a child of Run's ctx (context.WithTimeout(ctx, ...)), and
    relay.Conn.mailboxWait (relay/client.go:843-862) selects on ctx.Done() explicitly
    and returns immediately on cancel; commandRetryDelay's timer also selects on
    ctx.Done(). Not the culprit -- this is the ONE place in the loop that IS ctx-aware.
  - TerminalWatcher.run / Close (terminal_watcher.go:135-171): mirrors runJournal,
    selects on ctx.Done(); also inert for this specific test, since TestPhonesim_LaunchE2E
    never issues a terminal_watch, so no RunTerminal goroutine is even running.
  - lease.go:173 (LeaseConn.AwaitLease's `case <-time.After(timeout)`) and lease.go:238
    (WriteDataIn's submitframe.Gap time.Sleep): both are on the take_control/keystroke
    path, and TestPhonesim_LaunchE2E never takes control or sends input, so neither runs
    at all here. lease.go:173 is a bounded LeaseAwait-timeout wait, not a cancel-vs-wait
    race, but note it is likewise NOT selected on the Service ctx (AwaitLease takes only
    a time.Duration) -- the same class of defect as ForwardCommand, on a different path,
    outside this test's coverage.
  - The "grid-tap snapshot failed" log line: daemon.serve.go's periodic engine sampler
    (unrelated background goroutine, daemon-side, not part of remotegw.Service at all).
    Its rate is loosely correlated with slower runs only because both are downstream of
    general -race/CPU contention on the box, not causally connected to the shutdown path.

ROOT CAUSE, restated precisely: CommandForwarder.ForwardCommand (command_loop.go:56-58)
is a synchronous, non-cancellable interface call with no context.Context parameter.
Gateway.ForwardCommand (its production implementation) hardcodes its own 10s daemon-reply
deadline (gateway.go:363) independent of the caller's ctx. Every call site in
CommandBridge.Run's synchronous per-item dispatch (forward, and by the same shape
confirmLease -> LeaseConn.AwaitLease for take_control) can therefore block the whole
gateway shutdown for up to that call's own timeout -- 10s for ForwardCommand,
LeaseAwait (default 5s) for AwaitLease -- regardless of how promptly Service.Run's ctx
was cancelled. The 2s bound is not wrong; the two widened 5s copies did not fix
anything, they just made the flake rarer without removing the unbounded-by-ctx wait,
and 5s does not even fully cover LeaseAwait's own 5s default plus network latency, let
alone ForwardCommand's 10s.
