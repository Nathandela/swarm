== 3. Under the fuzz harness's access pattern ==

Stress mimicking a fuzz worker (the fuzz body, 8 goroutines, REP-burst inputs,
both emulators Closed every iteration), on a 16 GB machine:

  10s  iters=417   HeapAlloc= 9746 MB
  20s  iters=761   HeapAlloc=17635 MB
  30s  iters=989   HeapAlloc=22985 MB
  40s  iters=1137  HeapAlloc=26262 MB
  50s  iters=1889  HeapAlloc=43727 MB
  60s  iters=2068  HeapAlloc=47771 MB

2068 iterations x 2 emulators x ~12 MB = ~50 GB, which is the whole of
HeapAlloc: nothing is ever collected. That is what kills the fuzz worker.

== 4. Cause ==

NewEmulator does both of these:

  e.term.SetCallbacks(xvt.Callbacks{
      Title:            func(s string) { e.title = s },
      CursorVisibility: func(v bool) { e.visible = v },
  })
  ...
  runtime.SetFinalizer(e, func(e *Emulator) { _ = e.term.Close() })

The callback closures capture e, so e -> e.term -> Callbacks -> closure -> e is
a reference CYCLE, and e carries a finalizer. runtime.SetFinalizer documents
exactly this: "If a cyclic structure includes a block with a finalizer, that
cycle is not guaranteed to be garbage collected and the finalizer is not
guaranteed to run, because there is no ordering that respects the dependencies."
The Go GC therefore never collects any Emulator and never runs the finalizer.

Confirmed by removing the SetFinalizer line and nothing else: the 1026.0 MB
figure above becomes 0.3 MB, flat across all 30 rounds, and the no-Feed variant
becomes 0.3 MB flat across all 100.
