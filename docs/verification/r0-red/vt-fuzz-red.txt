Diagnosis:

This is NOT a split-boundary buffering bug (no partial escape or partial UTF-8 sequence is
involved). whole.Feed(data) alone -- with no split at all -- reproduces the same multi-second
stall; a throwaway probe (single Feed calls timed directly, deleted after use, no production or
test file left behind) measured wall time by CSI parameter digit count for
"\x1b[12" + <n zeros> + "I" (a plain CSI CHT -- Cursor Horizontal Tabulation, final byte 'I'):

    5 zeros  ->    5ms       6 zeros ->   58ms
    7 zeros  ->  1.08s       8 zeros ->  8.6s
    11 zeros -> ~9-15s

Growth is ~linear in the CSI parameter's numeric VALUE (roughly 10x per extra digit), which is
exponential in the number of digit characters typed -- because the digits "12" followed by k
zeros parse as the literal integer 12 * 10^k. Removing the \x7f (DEL) byte from the crasher does
not change the timing (9.48s vs 9.33s for 11 zeros), so DEL is incidental, not causal.

Root cause is in the vendored github.com/charmbracelet/x/vt@v0.0.0-20260713092006-0d683c34c74b,
not in this package's wrapper. Its CSI 'I' (CHT) handler is:

    // handlers.go:536
    e.RegisterCsiHandler('I', func(params ansi.Params) bool {
        n, _, _ := params.Param(0, 1)
        e.nextTab(n)
        return true
    })

    // csi_cursor.go:9
    func (e *Emulator) nextTab(n int) {
        x, y := e.scr.CursorPosition()
        scroll := e.scr.ScrollRegion()
        for range n {
            ts := e.tabstops.Next(x)
            if ts < x {
                break
            }
            x = ts
        }
        ...
    }

`n` is the raw CSI parameter value from untrusted PTY bytes, with no upper clamp. Once x reaches
the rightmost tab stop, charmbracelet/ultraviolet's TabStops.Next(x) keeps returning a value that
is never less than x (see the goroutine 33 stack above: stuck inside TabStops.Find/Next, called
from nextTab, called from the registered 'I' handler), so the `ts < x` early-exit never fires and
the loop runs the full, attacker-controlled `n` iterations regardless of the 80-column grid. A
single ~20-byte escape sequence (e.g. "\x1b[99999999999999999999I") is enough to make a Feed call
that a shim must process synchronously (Emulator.FeedChecked holds e.mu for the call's duration,
per emulator.go's own concurrency-model doc) spin for an attacker-chosen, effectively unbounded
amount of wall time -- freezing that session's Feed/Snapshot/Resize/Close, since FeedChecked's own
panic-recovery boundary (emulator.go:254 doc: "a malformed sequence ... must not be able to
terminate the daemon or shim") has no defense against a slow-but-not-panicking loop. CBT (final
byte 'Z', prevTab in csi_cursor.go) constructs its loop the same way and is presumably the same
class of bug, though not exercised by this specific crasher.

The fuzz property's own contract already treats this correctly: fuzz_test.go's header states
"Panics and deadlocks always fail" as an unconditional rule, layered on top of (not gated by) the
grapheme-cluster/malformed-UTF-8 whole-vs-split scoping. A multi-second-to-unbounded stall on a
single Feed call is exactly that class of failure; the whole-vs-split snapshot comparison itself
is a red herring here -- both sides eventually agree, they just take too long (or, for a longer
digit run, effectively forever) to get there. No fix applied.
