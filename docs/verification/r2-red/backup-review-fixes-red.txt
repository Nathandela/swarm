This is exactly the class of failure checkBackupNotTruncated exists to prevent: an UNRECOVERABLE
panic inside a bbolt background goroutine (created by tx.Check, called from validateBackup), which
propagates as a fatal, uncatchable process crash rather than a clean Go error -- the truncated file
passed the old (page-0-only) truncation guard and reached bolt.Open/tx.Check. The specific panic
message differs run to run depending on exactly where the cut lands relative to page boundaries
(the reviewer's own probe hit "assertion failed: Page expected to be: 7, but self identifies as 0");
this run hit bbolt's freelist page-type check instead. Both are the same root cause: a truncated
file reaching bbolt's internals uncaught.

FIX: parseBoltMeta and checkBackupNotTruncated (internal/remote/relay/backup.go) now parse BOTH meta
pages (offset 0 and offset pageSize), keep whichever ones validate (magic/version/checksum), and
size-check against the pgid of whichever has the HIGHER txid -- mirroring bbolt's own db.meta()
selection exactly, so the guard always judges the file bolt.Open will actually use.

After the fix, the same test (now included as part of the full backup_test.go, see below) passes
under `go test -race -count=1 ./internal/remote/relay -run TestBackup\|TestRestore` alongside all 19
other Backup/Restore tests, including the original TestRestore_RejectsTruncatedBackup (which is
immune to this specific gap because Tx.WriteTo always writes page 0's meta with the higher txid, so
it never exercised the page-1-active case).

FINDING 2 (BLOCKING): backupCreate always wrote to a fixed "<dest>.tmp" name and unconditionally
os.Remove'd whatever was there, so two Backup runs racing on the same destPath (nothing serializes
them -- Backup's ReadOnly Open takes a SHARED flock) could collide: the second run's Remove could
unlink the first run's in-flight temp file, and whichever run's os.Rename fired last could report
success (nil) over a truncated/wrong file, or fail outright with a spurious ENOENT despite a good
backup already sitting at the destination from the other run.

New regression test: TestBackupCreate_ConcurrentCallsDoNotCollide
  - Calls backupCreate(dir) twice in a row (simulating two overlapping Backup runs), writes to the
    first handle, and asserts (a) the two returned temp paths differ and (b) the first call's bytes
    are untouched by the second call.

This test targets backupCreate's NEW required signature -- func(dir string) (syncWriteCloser,
string, error), returning the actual unique path used (needed because os.CreateTemp's generated
name cannot be predicted the way the old fixed "<dest>.tmp" could) -- which the OLD implementation
(func(path string) (syncWriteCloser, error), taking a pre-computed fixed path) cannot satisfy at
all. Command against the unfixed backup.go:

  $ go vet ./internal/remote/relay/...
