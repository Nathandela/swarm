ROUND 4 -- reviewer finding fix-up: pre-auth allocation DoS on the XFF path
Date: 2026-08-15T09:18:30Z
Role: BUILDER (addressing reviewer BLOCKING finding on the proxy-quota work package)

Finding addressed by these two tests (see review, not reproduced here in full):
  BLOCKING: server.go:425 `xff := strings.Join(r.Header.Values("X-Forwarded-For"),
    ",")` followed by trustedproxy.go:84 `hops := strings.Split(xff, ",")` does
    O(header-size) allocation on an attacker-sized header, on the trusted-proxy
    path, BEFORE authentication and BEFORE serveConn's MaxConcurrentConnections
    admission check. s.httpSrv sets no MaxHeaderBytes, so net/http's 1 MiB
    default applies. Reviewer's throwaway probe measured a ~900 KB
    X-Forwarded-For header (450k comma-separated junk hops + a valid rightmost
    hop) through a trusted peer costing ~12.8 MB of allocation per connection,
    unauthenticated -- reachable because relay.config.example now ships
    trusted_proxies=["127.0.0.1/32"] on by default and Caddy forwards a
    client-supplied X-Forwarded-For verbatim. Before this work package the
    header was never parsed at all, so this is an entirely new surface.
  Requirement: bound the rightmost-hop extraction to O(1) allocation, and set
    http.Server.MaxHeaderBytes to a sane bound (the durable fix, since
    net/http's own ~1 MiB retained header buffer survives the Split fix alone).

Both fail for the intended reason:
  - the allocation test measures resolveSourceAddr's own extraction in
    isolation (runtime.MemStats TotalAlloc delta around one call): with the
    pre-fix `strings.Split(xff, ",")`, extracting the rightmost hop from a
    1.6 MB xff string (200,000 fabricated leftmost hops + the real one)
    allocates ~3.2 MB -- 2x the input, one slice element per comma -- against
    a 4096-byte O(1) bound;
  - the end-to-end test dials with a 200 KB X-Forwarded-For header (well
    under net/http's 1 MiB DefaultMaxHeaderBytes, so a pass here would prove
    nothing about a relay-owned bound) and the dial SUCCEEDS, because
    s.httpSrv sets no MaxHeaderBytes of its own and 200 KB clears the 1 MiB
    default with room to spare.

Fix: trustedproxy.go replaces `strings.Split(xff, ",")` + last-element index
with `strings.LastIndexByte(xff, ',')` + a subslice (same rightmost segment,
zero extra allocation instead of one slice header per hop). server.go sets
`s.httpSrv.MaxHeaderBytes = maxRequestHeaderBytes` (32 KiB, a new const),
replacing net/http's 1 MiB default so the retained parse buffer itself is
bounded regardless of how the header is later processed.
