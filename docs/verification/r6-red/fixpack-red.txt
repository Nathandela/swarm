MEDIUM 6 (the spool file's CREATION is not durable: MkdirAll + O_CREATE with no
fsyncDir, so a power loss after the very first acked post can lose the file's
directory entry entirely). There is no portable way to assert a directory fsync from
a Go test -- an unsynced directory entry is indistinguishable from a synced one until
the machine actually loses power. The fix is by inspection and by symmetry with
Compact, which already fsyncs the directory after its rename. No test claims to
prove it, and none is written that would pass either way.

0600/0700 filesystem permissions are the PRIMARY control on this socket and the

internal/shim/hookspool.go prose. What IS tested is that the token now exists and is
enforced end to end (section C).

C. FINDINGS WITH NO FAILING-FIRST RUN, STATED HONESTLY
--------------------------------------------------------------------------------

The bounded seen-set's OVERFLOW behavior (the floor advancing to the lowest retained
above-floor sequence, which assumes everything below it was seen) is asserted only in
the direction that matters -- the live window is never swallowed. The residual it
admits is documented at hookSeen.add rather than tested: past 256 sequences ingested
with a permanent hole below every one of them, the structure degrades back to the
round-1 high-water assumption. No test pins that degraded corner, because pinning it
would be pinning the very behavior the round-2 fix exists to remove.

The residual loss window that survives R2-BLOCKER 2 is likewise documented, not
tested: if the DAEMON dies while a session is running, and the session then ends
while the daemon is still down, the restarted daemon finds a retired session that its
engine will not register, so nothing authenticates a replay of that spool. That is a
structural limit of the ack contract (a callback must authenticate against a live
engine session), not a hole the final drain could close, and it needs both failures
at once rather than the every-time loss the reviewer proved 5/5.
