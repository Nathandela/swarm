===========================================================================================
2. THE FIX
===========================================================================================

Not a fourth widening of s23MetricConst. The pattern is unchanged; what changed is that its
blind spots are no longer silent. Two checks, neither of which looks at declaration syntax:

  TestPBDS7_EveryMetricSpendResolvesToADeclarationTheScanSaw
      every `KitMetrics.<ident>` reference in the eleven fenced files must be a name
      s23ScanMetrics RETURNED from inside `object KitMetrics`. An unrecognised declaration is
      absent from that set, so its spend is a dangling reference and fails. This is not the
      Kotlin compiler's check -- kotlinc resolves the name perfectly well -- it is the GATE's
      blindness made observable.

  TestPBDS7_EveryNumberInTheKitIsAccountedFor
      every numeric literal token in those files must be the value of a recognised declaration
      or one of nine exempt bare literals (s23LiteralExemptions), and inside object KitMetrics
      not even that. An unrecognised declaration leaves its number unaccounted for.

Plus one adjacent fail-open found while reading s23ScanMetrics and closed in the same change: a
pending `origin:` annotation used to survive unmatched lines and be inherited by the next
declaration, so `const val NEXT_DP = 7f` after an unmatched wrapped declaration passed against
`.pdot { width }`. A pending annotation now dies on the first non-blank line of CODE; comment
lines are blank in the stripped view, so a KDoc block between an annotation and its declaration
still carries.

Counts against the shipped kit, read by the shipped functions: 11 fenced files, 62 numeric
literal tokens, 17 of them bound to recognised declarations, 45 exempt across the nine rows;
12 members recognised inside object KitMetrics; 18 spends.

STILL GREEN, and this is the exact boundary written on s23MetricConst and s23LiteralExemptions.
All three conditions are needed: inside object KitMetrics it fails (5d); with a value off the

the exemptions position-scoped, which is a per-line permission list and is the thing this whole
sequence of rounds is about not building.

-------------------------------------------------------------------------------------------
6b. Other boundaries, stated with their reason
-------------------------------------------------------------------------------------------

  - A spend written without the `KitMetrics.` prefix -- a member import, or a reference from
    inside the object itself -- is not seen by the spend check. Its declaration still faces the
    literal accounting, which inside the object has no exemptions.
  - Only the eleven files s23OwnedFiles names are scanned. Motion.kt is PB-DS-8's, for the
    reason the package comment gives, and app code outside ui/kit is other slices'.
  - s23CodeNoStrings blanks string contents, so a number inside a `${...}` template expression
    is not counted. Raw strings are refused outright: s23KitLiterals fails the test rather than
    scan a source it would misread.
  - A number that never becomes a property at all -- `Kit.dp(context, 7f)` -- is
    TestPBDS7_NoMetricIsTypedAtADpCallSite's, unchanged by this work.
  - This is a FILE gate. What a component resolves on a running resource table is PB-DS-10's,
    in app/src/test/.../ui/kit/, and nothing here speaks to it.
