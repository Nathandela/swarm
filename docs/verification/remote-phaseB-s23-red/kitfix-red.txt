Seven failures, and what each says:

  - `private const val DOT_DP = 7f` is not seen by the scan at all. This is the shipped
    defect: Kit.kt:89 `private const val ATTENTION_BORDER_SHARE = 0.36f` was never matched,

  - `private val DOT_DP: Float = 7f` likewise -- the same number wearing different clothes.

  - BADGE_HEIGHT_DP passes at 20f against a row that states `height 16`; so does a citation
    that names no field of the row, and one that names a field the row does not state.

4. The Robolectric lane -- A PREDICTION, written before the lane was run
===========================================================================================

READ THIS SECTION AS A PREDICTION AND NOT AS A RESULT. It was written while another agent
held the Gradle lane, and it says what each suite MUST report against the shipped kit. It is
kept rather than replaced, for a reason that is the point of this whole file: an independent
re-auditor applied the same mutations in a throwaway worktree and found these predicted
strings matched CHARACTER FOR CHARACTER -- compare the four KitDensityTest lines below with
their ledger. That establishes both halves at once: the predictions were true, AND a true
prediction is still not evidence. Deleting it would erase the second half. Section 5 is the
run.

$ ./gradlew :app:testDebugUnitTest --tests 'dev.swarm.phone.ui.kit.*'

DEFECT 1 -- the status dot's glow does not render.
  New: InboxRowTest.`the live Groups' glow survives into the layer, and the flat Groups paint
  no halo` draws the dot into a bitmap the size of its own layer and counts painted pixels
  outside the 7dp core. Against the shipped geometry it must report:

      the layer is 7px and a 7px core with a 9px halo needs 25px. A software layer's bitmap
      IS the view's bounds, so the halo is clipped inside the layer -- before clipChildren on
      any parent is consulted, and with the Paint, the shadow radius and the layer type all
      correct.

  and InboxRowTest.`the status dot is the design's 7dp mark in its Group's colour` must fail
  on the footprint claim, because the shipped view was 7dp with no compensation.
  The control, `the pixel probe rejects the geometry that clipped the glow`, rebuilds that
  geometry from the kit's own drawable and requires the same haloFaults() to object -- it
  must PASS both before and after the fix, and it is what says the probe was not written to
  agree with whatever the kit does.

DEFECT 2 -- the self-comparisons.
  InboxRowTest.`only the live Groups glow, and only they are on a software layer` now takes
  the colour, the radius and WHICH Groups glow from KitOrigin.dotGlow(token), which reads the
  `.pdot.*` variant whose fill is the Group's token. Perturbation to check the new expectation
  is not the old one: change Kit.glowShare's needs_input branch to 0.60f and this test must
  fail; before the change it passed, because the expected value was the same call.

DEFECT 5 -- truncation where the platform rounds.
  New suite KitDensityTest, @Config(qualifiers = "420dpi") (density 2.625). Against the
  shipped kit its four tests must report, among others:
      `.prow` hairline: design says 3, component resolved 2
      `.prow` padding-x: design says 32, component resolved 31
      `.workbar` height: design says 8, component resolved 7
      `.ptabs svg` size: design says 58, component resolved 57
  Its first test asserts the qualifier took, so a Robolectric that ignored it fails loudly
  rather than passing at mdpi where truncation and rounding coincide.

DEFECT 6 -- the accessibility defaults.
  InboxChromeTest.`the tab badge is announceable whether or not the screen gives it words`
  must fail on the shipped `item.badgeDescription ?: ""` with the badge's description being
  "" rather than null. InboxRowTest.`the status dot announces the state when the screen names
  it` must fail on the shipped statusDot(), which takes no description at all -- it does not
  compile against the two-argument factory, which is the RED a missing parameter produces.

A CAVEAT THAT BEARS ON EVERY COUNT ABOVE, and on every count in every file like this one.

Earlier the same day, two Gradle processes collided over android/app/build. Afterwards:

  - compileDebugUnitTestKotlin restored FROM-CACHE with an EMPTY output,
  - Gradle reported `testDebugUnitTest NO-SOURCE`,
  - and the full `./gradlew test` exited 0 having executed ZERO debug tests.

A successful-looking build that ran nothing. Clearing it needs app/build/tmp/kotlin-classes/
debugUnitTest and --no-build-cache; deleting app/build/kotlin alone does not.

This is the same failure class the assertions in this slice were written against, one layer
up: `NO-SOURCE`, a FROM-CACHE compile with no output, a regexp that stopped matching, and a
claim list that iterated zero times are all GREEN BECAUSE NOTHING RAN. The guard is the same
in every case -- assert a non-zero EXECUTED test count rather than an exit code. Any count
taken after a collision, without checking that the task actually executed, is worthless. The
run recorded above was checked. The guard itself is filed, not built.
