S24 RED/GREEN -- the SETTINGS and PAIRING screens (PB-DS-6, PB-DS-9)

This is the second half of S24. `screens-model-red.txt` and `screens-gate-red.txt` in this
directory cover the triage inbox and the PB-DS-11 fence; this covers the two screens
recomposed after it.

HOW THE KOTLIN RUNS WERE PRODUCED, EXACTLY -- the same way, and for the same reason. The
Kotlin lane is sequenced by another agent and this slice may not invoke ./gradlew, so each
model suite was compiled and run on a plain JVM with the kotlin-compiler-embeddable and junit
jars the Gradle cache already holds and the JDK android/toolchain.env pins. `SettingsPanel`
and `PairingPanel` are pure Kotlin -- no Android import, no resources, no Robolectric -- so
the classes that ran are the classes the Gradle lane compiles. android.jar is on the COMPILE
classpath only, because `PermissionState` and `ScannerState` are declared in files that also
name `android.Manifest`; no android class is loaded at run time.

The RED runs use the implementation as it was committed for them: every signature present,
every copy table real, `of()` a single TODO(). So the failures are NotImplementedError --
missing behaviour rather than unresolved references, which is what makes them evidence rather
than a syntax error. Both files are a re-run of the FINAL assertions, so what is recorded is
the wording the tests ship with.

WHAT THE GATE RED RUN DOES AND DOES NOT SHOW, said plainly.

TestPBDS6_EveryRecomposedScreenIsBuiltOutOfTheKit fails on the pre-slice tree, and it fails on
the clause that matters: the two screens its composition table claims did not exist, so their
components were checked against nothing. That is the same defect PB-DS-6 was recorded NOT MET
over, one screen further along -- a table of components nobody renders.

TestPBDS9_AScreenComposesWhatIsOnItRatherThanHidingWhatIsNot PASSES on the pre-slice tree, and
that is recorded rather than dressed up. The screen package then held one file, the triage
inbox, and it never wrote a visibility. The three `render*Step` functions this fence is about
were in PairingSurface, which is a SURFACE and is deliberately outside this fence's tree -- a
surface owns controls whose visibility is a fact about the device rather than about the step
(the camera preview is the standing example). So this assertion is a fence against the pattern
coming back into the screen package, not a fix of a violation that was in it. Its negative
control is where its strength is demonstrated.

Both control assertions pass on both trees, which is what a control is for: they run against
synthetic sources and are independent of the tree.

4. WHAT IS NOT EVIDENCED HERE
===============================================================================

- `SettingsPanelView.kt` and `PairingPanelView.kt` have NOT been run. They are Android views
  and need the Gradle lane. What has been verified without Gradle is that they TYPE-CHECK:
  both compile against android.jar with the two kit signatures they call (`navHeader`,
  `sectionLabel`) declared exactly as ui/kit declares them. Whether they put the right things
  on screen in the right order is unanswered, and there is no Robolectric suite for either --
  that is a gap, not an omission I expect a reader to overlook.
- `SettingsSurface` and `PairingSurface` have not been compiled at all. They import
  `swarmmobile`, which is the gomobile AAR, and it cannot be built on this JVM harness.
- No screen here is fully PIXELED. The kit ships the triage inbox's components and no others,
  so derivation rows 4 (toggle), 9 (text field), 10 (CTA buttons), 15 (settings row) and 18
  (mono well) have no factory, and the views those rows specify arrive at both screens as
  parameters from their surface, unstyled or carrying only the text appearance the surface may
  legally spend. PB-TOK-3's `terminal_peek` binding is untouched for the same reason.
