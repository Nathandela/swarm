Three of the four failures above are the three gaps. The PASS in the middle is deliberate and
is the point of running it in the same command: the path tokeniser is the whole comparison,
so it is proved to work BEFORE anything is compared through it. It asserts, among other
things, that the artifact's own Settings path and the spelling Android can parse are the same
drawing:

    tabbarPathTokens("M12 8a4 4 0 110 8 4 4 0 010-8z")
      == tabbarPathTokens("M12,8 a4,4 0 1 1 0,8 4,4 0 0 1 0,-8 z")
      == "M 12 8 a 4 4 0 1 1 0 8 4 4 0 0 1 0 -8 z"

and that five one-edit perturbations of it (a coordinate, a radius, one arc flag, the closing
`z`, relative vs absolute) do NOT compare equal to it.

WHY THAT MATTERS RATHER THAN BEING PEDANTRY. `110` in the artifact's arc is not the number one
hundred and ten: SVG lets an elliptical arc's two flags run together with the parameter after
them, so it is `1`, `1`, `0`. Android's PathParser reads an arc's seven parameters as seven
plain numbers and does not implement that rule, so pasting the artifact's own spelling into a
VectorDrawable draws a different shape on the device -- silently, with no error anywhere. The
drawable therefore separates the flags and the gate compares token streams, which is what lets
the file be provably the artifact's drawing rather than a hand-adjusted lookalike.


3. The bar's bottom padding doubled -- and what it was resolved to
--------------------------------------------------------------------------------------------

The third failure above. `.ptabs { padding-bottom: 14px }` reserves the iPhone home indicator
INSIDE the bar's own 74 px box, and `PhoneActivity.insetTheSystemBars` pads the whole surface
by the real `WindowInsets.systemBars` bottom -- roughly 24 dp under gesture navigation, roughly
48 under three buttons. Both applied.

RESOLVED IN FAVOUR OF THE SYSTEM INSET, from the design's own text. Derivation row 19 has
already ruled on this class of constant: "`screen_top` 54 is an iPhone notch constant -- on
Android it must come from `WindowInsets.statusBars`, with 54 as the design-time preview value
only. `screen_bottom` 76 is the same problem against the gesture-nav inset." Row 20 says where
the bottom one lands: the scaffold spends "bottom `screen_bottom` (or inset + `tabbar_height`)"
-- the measured inset UNDER a bar that is `tabbar_height` tall, not a constant inside it.

So the bar spends `tabbar_height` and nothing else. The gate asserts BOTH halves, because the
defect is the pair and either half alone is correct: TabBar.kt calls no `setPadding` at all,
and PhoneActivity.kt still passes `bars.bottom` into the surface's padding -- that listener is
now the bar's only bottom air, so deleting it would drop the inset everywhere at once.

The ledger row that required the old spending, `{"TabBar.kt", ".ptabs", "padding-bottom", 0,
"swarm_space_14"}` in s23_kit_test.go, was removed by its owner with the derivation recorded in
its place; this task did not touch that file.
