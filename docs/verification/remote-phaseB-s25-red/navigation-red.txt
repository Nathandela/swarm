# S25 tab navigation: failing-first run (GG-5)

Recorded before ui/screens/PhoneScaffoldView.kt existed and before TabItem carried a tap handler.
Three runs, because the change has three failing halves and each one had to be red for its own
reason rather than as a consequence of the others:

  1. the HOSTED half -- the app the user opens has no tab bar on it at all, and no tab does
     anything. Written against symbols that already existed, so it fails at RUNTIME rather than at
     compilation: a missing-constant error would not have told us whether the bar was absent or
     merely renamed.
  2. the GATE half -- android/gate/s24_screens_test.go's composition table is where this project
     records which file composes which component, so the `tabBar` row was moved off
     TriageInboxView.kt and onto the scaffold BEFORE the scaffold existed.
  3. the COMPONENT half -- the scaffold's own suite, against a factory nobody had written.

THE THIRD RUN IS A COMPILATION FAILURE AND THAT IS WHAT A MISSING FACTORY IS. It is recorded as it
came out rather than being converted into something that looks more like an assertion.

## 4. The Machines destination, after review: a blank primary tab

Recorded after the three runs above were green. The Machines destination navigated and drew
NOTHING, on the argument that its screen cannot be built honestly (App.Presence is a blocking relay
round-trip the ledger forbids calling per redraw; pairedDeviceName has no bound accessor --
agents-tracker-xtj). That part stands. What did not stand is what the user was left looking at: a
blank area under the bar, on every tap, indistinguishable from a crash or a failed load. PB-DS-9
rules the other way for exactly this case -- an empty section is still a section -- and the activity
screen next door already obeys it.
